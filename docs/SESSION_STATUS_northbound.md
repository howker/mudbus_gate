# Статус northbound-треков: Акрон (готово) и ВКМ-360 (пауза)

_Сводка на конец сессии 25.07.2026. Документ для демонстрации результата и возобновления работы._

---

## 1. Акрон-01 northbound — ✅ ЗАКРЫТ, подтверждён на реальном приборе

Шлюз (`mbgw`) изображает «Акрон-01» перед ПК «Энергосфера» по Raw TCP
(голый Modbus RTU, команды 101/03/102/104/106/110). Реальный прибор
подключён, обмен идёт.

**Что подтверждено живьём (19.07.2026, northbound на тестовых данных):**

- Идентификация (101), паспорт, версия, заводской номер.
- Текущие значения (102/03).
- Дозабор почасового архива (104): ЭС прошла от вершины вглубь одним
  проходом; «Отставание» упало до штатного лага (~54 мин).
- Живое время прибора — принимается ЭС без разбежки.

**Что подтверждено живьём (26.07.2026, ПОЛНЫЙ ЦИКЛ на реальном приборе):**

- **Southbound**: `mbgw run` реально читает Акрон-01 по COM105 (виртуальный
  порт через Ethernet/RS-485 конвертер), почасовой архив **побайтово
  совпал** с эталонным отчётом штатного ПО производителя (10/10 строк).
- **Веб-дашборд** (`internal/web`) показывает живые показания в реальном
  времени; починена совместимость с Internet Explorer (единственный
  браузер на целевой платформе Windows Server 2008 R2/2012 — он не
  поддерживает `fetch`/`async-await` ни в одной версии).
- **Северный+южный контур одновременно**: два процесса `mbgw.exe`
  (southbound `run` + northbound `--serve-akron`) делят один файл
  `mbgw.db` без конфликтов — включён `PRAGMA journal_mode=WAL` +
  `busy_timeout=5000` (не через DSN-параметры — `modernc.org/sqlite`
  не гарантированно поддерживает синтаксис `mattn/go-sqlite3`).
- **ЭС реально переключена** с прямого RS-485 на наш northbound-carrier
  (`RawTCP 127.0.0.1:15021`) и **успешно опрашивает через шлюз**:
  идентификация принята, часы синхронны («Время УСПД отстаёт на 0-1 сек»).
- **Дозабор глубокого архива**: у прибора обнаружен реальный лимит **27
  строк за один запрос** (документация заявляет 31 — расхождение
  подтверждено подбором через `akronread --hourly N`, без единой
  пересборки). Инструмент `tools/akronbackfill` постранично (по 27)
  забрал 170 часов реальной истории и сохранил в `archive_hourly`.
  **Результат: «Основные интервалы» в ЭС сдвинулись с 19.07.2026 на
  26.07.2026 16:00, отставание упало с 7 суток до 48 минут.**

**Артефакты в репозитории:**

- `internal/northbound/akron_live.go` — production-ответчик (паспорт +
  текущие + часовки + живые часы), backed by SQLite (не тестовые
  фикстуры).
- `internal/device/akron_hourly.go`, `internal/poller`, `internal/scheduler`,
  `internal/channel`, `internal/lease` — T11-минимум: центральный
  планировщик опроса (не тикер на устройство), полностью реализован для
  одного прибора, готов расти до multi-device.
- `internal/config/config.go`, `cmd/mbgw/run.go` — конфиг умеет COM-порт
  (`kind: rtu_serial`, `com`, `baudrate`, `parity`, `stopbits`),
  настраиваемый `unit_id`, флаг `--config <path>` (чтобы не конфликтовать
  с уже существующим тестовым `config.yaml` для 4 мок-приборов).
- `internal/storage/sqlite/repo.go` — WAL + busy_timeout через явный
  `PRAGMA`, а не DSN-параметры.
- `internal/web/server.go` — диагностический дашборд, IE-совместимый
  (`XMLHttpRequest`, без `fetch`/`async-await`).
- `tools/akronread` — southbound-диагностика реального прибора
  (идентификация/текущие/архив, декодирует через тот же боевой путь,
  что и планировщик); флаг `--save-passport` пишет паспорт в БД (нужен
  northbound-carrier'у для ответа на команду 101).
- `tools/akronbackfill` — постраничный дозабор глубокой истории архива с
  реального прибора в обход обычного цикла поллера (который берёт только
  самую свежую строку за цикл); `--page-size` настраиваемый (по
  умолчанию 27 — подтверждено для этого прибора/прошивки 6.6, НЕ
  гарантированно универсально).
- `config.akron_real.yaml` — конфигурация запуска southbound для
  реального Акрона на COM105.
- `tools/seedakron`, `tools/addhour` — наполнение БД тестовыми данными
  (для симуляции без реального прибора).
- `docs/M3_DISCOVERY_FINDINGS_akron.md`, `docs/M4_LIVE_CONFIRMATION_akron.md`.

**Ключевые уроки (часть переиспользована из ВКМ, часть — новые):**

- Прибор должен отдавать паспорт до того, как драйвер продолжит.
- На неизвестный регистр — не молчание (таймаут → reconnect), а корректный
  ответ/исключение.
- Живое время прибора должно совпадать с сервером опроса, иначе опрос
  останавливается.
- «Зацикливание на i=135» было нехваткой глубины seed-данных, не проблемой
  протокола.
- **Документированные лимиты прибора не гарантированно верны для
  конкретной прошивки** (31 в доке vs 27 реально) — нужно предусмотреть
  подбор/настройку в профиле устройства, не хардкодить из документации
  бездумно. Отдельная будущая задача: `max_archive_rows_per_request` как
  поле профиля, не константа в коде.
- Два процесса `mbgw.exe`, делящие один SQLite-файл, требуют явного
  `PRAGMA journal_mode=WAL`/`busy_timeout` — DSN query-параметры зависят
  от конкретного драйвера и могут молча игнорироваться.
- COM-порт нельзя делить между процессами (в отличие от SQLite) — при
  дозаборе/диагностике southbound-поллер нужно временно останавливать.

### Незакрытые пункты (следующие шаги)

- **Дозабор — сейчас ручной инструмент**, не встроен в обычный цикл
  поллера. Постоянное решение: настраиваемая в МШ глубина архива на
  прибор + автоматическое обнаружение реального лимита строк за запрос
  (а не падение с необъяснимым исключением, если лимит завышен).
- **Единый процесс**: southbound (`run`) и northbound (`northbound
  --serve-akron`) сейчас два отдельных `mbgw.exe` — по плану должны
  объединиться в один процесс, поднимающий обе стороны по конфигу.
- **Windows Service** — по ТЗ явное требование, пока не сделано (заготовка
  `install-service`/`service_windows.go` в проекте уже есть).
- «Мало байт» — новый, не до конца разобранный симптом в протоколе ЭС
  (наблюдался периодически в процессе отладки) — не блокирует достигнутый
  результат, но не исследован до конца.

## 2. ЭЛЕМЕР-ВКМ-360 northbound — 🔶 МЕХАНИКА ГОТОВА, ждём реальный прибор

Схема (по совету производителя): ЭС читает ВКМ-360 через **драйвер
УВП280А.01-МЭ** по Modbus TCP (MBAP). Реальный ВКМ **отключён** — вся
работа велась на тестовых данных.

**Что реализовано и проверено (юнит-тестами + живым обменом с ЭС):**

- Транспорт MBAP; идентификация (1806-1811); хендшейк-константы (100-117).
- Живые часы (1800-1805) + синхронизация времени (1007/1008/1009);
  **год кодируется двумя цифрами** (`year_mode = y2000`) — критично.
- Текущие параметры трубы (2000-2599, FC04): давление (+0/+2),
  температура (+4), энтальпия (+6), расход (+8), масса (+10),
  мощность (+16), **тепловая энергия (+18)** — заполнены реальными
  значениями (раньше были нули → давление и энергия «не читались»).
- Архивный протокол целиком: запись запроса (7900-7914, FC16),
  статус (8000, honors qty + эхо id 8001), длина (8002), строка (8003+).
- Строка архива по спецификации `registri_mbrrtu_vkm.pdf`: период первым
  (`T=начало-конец`), единицы без пробела, NUL в конце, **Windows-1251**,
  формат по битам опций из запроса ЭС (opts=12: тэги без шапок).
- Карта параметров (7600/7700/7800) — чтение имён/значений.
- Файловый конфиг `vkm_config.txt` (правится на сервере без пересборки):
  `year_mode`, `clock_offset_sec`, `min_ready_ms`, `period_format`,
  `time_layout`, `archive_string`. Стрипается UTF-8 BOM (PowerShell
  `Set-Content -Encoding UTF8` его добавляет и ломает первую строку).
- Лог обмена `vkm_live.jsonl` с лимитом 4 МБ.

**Где остановились:** ЭС проходит весь обмен (время 0 сек, доходит до
чтения строки архива), но отвергает архивную строку с «Неверный формат
пакета». Детальной причины в логах ЭС **нет** — сообщение терминальное
(проверено: `sexec_Prot.txt` — только SQL с этим же текстом;
`stkuse_TProtReader.txt` — служебный лог; трассировка `getr95.rar`
разобрана вручную).

**Единственная оставшаяся неизвестность:** точный словарь тэгов и формат
значения, который ждёт именно этот драйвер УВП280А.01-МЭ. В открытой
документации его нет; тэги `M`/`t` — наша догадка.

### План возобновления (когда ВКМ появится в сети, ожидается ~в течение недели)

1. **`tools/vkmprobe`** (по образцу `akronprobe`) — прямой клиент к
   реальному ВКМ: проходит 7900→8000→8002→8003, печатает, что прибор
   ответил (реальные тэги/формат строки). Безопаснее и быстрее всего.
2. При необходимости — режим **`--tap`**: прозрачный перехватчик
   ЭС↔прибор с логированием обеих сторон (снимает и запрос ЭС, и ответ
   ВКМ на живых данных). Риска не добавляет — записи в 7900-7914 и сегодня
   идут от ЭС в прибор напрямую.
3. По реальной строке — поправить `BuildVKMArchiveString`/`defaultVKMParams`
   и/или разложить параметры между архивом (масса) и текущими
   (температура/давление/энергия).

**Пользователь пришлёт IP:порт прибора — `vkmprobe` готовится заранее.**
