## 0. Что это за документ и как им пользоваться

Это НЕ замена существующим проектным документам

- фиксирует **конкретные архитектурные решения**, принятые в процессе

- фиксирует **факты, подтверждённые эмпирически** в процессе разработки

- фиксирует **правила совместной работы** в этом конкретном формате
  (терминал + человек-посредник без прямого доступа модели к серверу) —
  раздел 4;
- описывает **окружения** (разработка, git, тесты, прод) — раздел 5;
- даёт **хронологию по спринтам**, включая явное указание, на чём
  остановились прямо сейчас — раздел 6;
- фиксирует **известный технический долг** — раздел 7.

## 1. Отклонения реальной реализации от исходного ТЗ (`FINAL_TRD.md`)

Важно прочитать это ПЕРЕД `FINAL_TRD.md` — иначе можно принять
устаревшие пункты исходного ТЗ за актуальное состояние проекта.

`FINAL_TRD.md` писался как техническое задание на **абстрактный
многоприборный MVP** для рынка АСКУЭ/АИИС КУЭ вообще — до появления
конкретного заказчика с конкретными приборами и конкретной системой
учёта (Энергосфера, `CSD_Astrakhan`). По мере работы с реальным
заказчиком проект прагматично отклонился от части исходных решений —
не из-за ошибки планирования, а потому что **реальные ограничения
заказчика оказались конкретнее и жёстче**, чем абстрактный MVP мог
предвидеть.

| Пункт FINAL_TRD | Что решено вместо этого | Почему |
|---|---|---|
| Web UI: TypeScript SPA, `go:embed web/dist` (§ FINAL_TRD п.2) | Admin UI — один Go-файл (`internal/web/api_admin_ui.go`) с HTML/CSS/ES5-JS как строковый литерал, отдаётся напрямую | Целевая площадка — старый Windows Server с Internet Explorer как единственным доступным браузером у оператора. Полноценный SPA-тулчейн (сборка TS, современный JS) избыточен и не нужен для одного узкоспециализированного admin-экрана; ES5 без async/await/fetch — осознанное ограничение под IE |
| REST API по OPENAPI.yaml, TLS обязателен (§3.4) | Простой `net/http`, без TLS, слушает `127.0.0.1:<порт>` | Единственный потребитель — сам оператор на этой же машине через браузер; сеть изолированная, заказчик не просил TLS. Может быть добавлено post-MVP, если периметр изменится |
| RBAC/роли/аутентификация (§3.4) | Отсутствует полностью — `/admin` открыт без логина | Тот же периметр — один оператор, один сервер, без сетевого доступа извне. Формально это осознанный риск, не забытая задача |
| PostgreSQL/TimescaleDB опционально (§2) | Только SQLite (`modernc.org/sqlite`), никогда не рассматривался Postgres всерьёз | Объём данных (единицы приборов, получасовые архивы) далёк от того, где потребовалась бы отдельная СУБД; упрощение эксплуатации важнее |
| Интеграция наружу: MQTT/gRPC/extDB — post-MVP (§3.2) | **extDB реализована в MVP и является ЕДИНСТВЕННЫМ работающим путём доставки данных в систему учёта** (`internal/integration/extdb.go`, `energosphere_sync.go`) | Родной драйвер Энергосферы (ЭС) для части каналов (тепло/давление ВКМ) отказался принимать данные независимо от их содержимого — проверено исчерпывающе (см. раздел 3). Прямая запись в БД ЭС — единственный подтверждённый рабочий канал, а не запасной вариант «на потом» |
| Единый абстрактный список из 4 приборов (ВКМ-360, ИВК-ТЭР, ТСРВ-024, Меркурий), профили равнозначны | Реально в проде эксплуатируются **ВКМ-360** и **Akron** (последнего в исходном списке 4 приборов не было вообще) | Заказчик пришёл с конкретным парком приборов, отличным от исходного планового списка. ИВК-ТЭР/ТСРВ-024/Меркурий остаются в кодовой базе как поддерживаемые профили, но не подтверждены на реальном оборудовании этого заказчика |
| Failover канала входит в MVP, failback выключен по умолчанию (§5) | Реализовано в общем виде через `internal/channel`, но НЕ упражнялось на реальном оборудовании этого заказчика — только один канал на прибор в проде | Формально код есть, но подтверждённого факта работы failover на реальном канале связи этого заказчика нет — см. технический долг (раздел 7) |
| Аудит изменений конфигурации — входит в MVP (§3.4) | Не реализовано | Заказчик не запрашивал; отложено, не забыто — см. технический долг |
| Разработка «без реальных приборов», только через симуляторы (§2) | Разработка и отладка **на реальных приборах заказчика**, удалённо через оператора-посредника (человек на месте выполняет команды в PowerShell, модель не имеет прямого доступа к сети/приборам/серверу) | Единственный практичный способ найти реальные проблемы (например, находка эпохи секундного формата Time= у ВКМ, структура PointMains в ЭС) — симулятор не мог бы вскрыть эти детали, они специфичны для КОНКРЕТНОГО экземпляра оборудования заказчика |

**Важный вывод из этой таблицы**, значимый для дальнейшей работы: этот
проект прошёл путь от «абстрактного мультиприборного MVP» к
«конкретному промышленному шлюзу для одного заказчика» — архитектурная
гибкость исходного профиль-ориентированного ядра (Protocol HAL,
`internal/profile`) сохранена и оправдала себя (новый прибор Akron
добавился без изменения ядра), но периферийные решения (web UI, TLS,
RBAC, способ доставки в систему учёта) переопределены под реальность,
а не под первоначальный абстрактный план.

## 2. Архитектурные решения, принятые в процессе (не отражены в исходных LLD/CONTRACTS)

### 2.1. Единый режим запуска `mbgw server` вместо связки из отдельных команд

Первоначально предполагалась связка `run`/`serve`/`northbound`/
`es-sync` как отдельных процессов. В проде используется **только**
`mbgw server` — единый процесс, конфигурация целиком из SQLite БД
(devices, каналы ЭС, подключение к ЭС — всё редактируется через
`/admin`, ничего через YAML/текстовые конфиги вручную). Остальные
команды (`run`, `serve`, `es-sync` с текстовым конфигом) оставлены в
`main.go` для обратной совместимости/разработки, но не являются
рекомендуемым способом эксплуатации.

### 2.2. Прямая запись в БД ЭС вместо эмуляции прибора — для ОБОИХ типов приборов

Исходно (первая реализация): ВКМ — прямая запись в SQL Server ЭС
(таблица `Mains`); Akron — эмуляция физического прибора по протоколу
АКРОН-01-1, чтобы **родной драйвер ЭС сам** подключался и забирал
данные (`internal/northbound/akron_live.go`).

**Решение от 2026-08-31 (прямой запрос оператора):** оба типа приборов
переведены на ОДИН механизм — прямую запись в БД ЭС
(`internal/integration/energosphere_sync.go`, обобщён под оба
источника данных). Старый Akron-northbound путь **не удалён**, а
закомментирован в `cmd/mbgw/server.go` (единственный вызов
`startAkronNorthboundForDevice`) — сама функция и весь код northbound
остаются в дереве проекта на случай, если понадобится вернуться.

Причина: единообразие проще поддерживать, чем два разных пути доставки
данных с разной логикой отладки; плюс родной путь ЭС для Akron не был
структурно необходим — прямая запись работает так же надёжно, как уже
подтверждено для ВКМ.

### 2.3. Целевая таблица ЭС: `PointMains` (`ID_PP`) вместо `Mains` (`ID_Channel`)

**Решение от 2026-08-31 (прямой запрос оператора).** Заказчик указал
новую целевую таблицу в ЭС: `dbo.PointMains` со столбцами `ID_PP`
(int), `DT` (datetime), `Val` (float), `State` (int) — вместо ранее
использовавшейся `dbo.Mains` (`ID_Channel`/`MeasureDate`/`Value`/
`State`). Подтверждено напрямую в SSMS запросом к `PointMains` (см.
раздел 3 — точная структура).

`internal/integration/extdb.go`: тип переименован `MainsWriter` →
`PointMainsWriter`, все SQL-запросы переведены на новую таблицу и
колонки.

**Отдельная деталь подключения, тоже без объяснения причины «на
глаз» — зафиксирована прямо в коде** (`extdb.go`,
`OpenPointMainsWriter`): подключение к SQL Server ЭС идёт с
`encrypt=disable`. Причина — целевая база работает на **SQL Server
2008 R2**, версия которого старше, чем ожидания драйвера по
умолчанию для TLS-подключений (современный mssql-драйвер по умолчанию
пытается TLS, старый сервер этого не понимает — согласование
шифрования падает). Безопасно отключать здесь только потому, что
подключение остаётся в пределах `localhost`/изолированной сети
заказчика — не следует переносить эту настройку бездумно в проект
с другим периметром безопасности.

### 2.4. Обобщённая модель «точка ЭС» вместо VKM-специфичных «каналов»

Раньше сопоставление «параметр прибора → номер в ЭС» существовало
только для ВКМ (4 захардкоженных поля `ChanHeat`/`ChanMass`/
`ChanTemp`/`ChanPressure` в `integration.Config`), таблица
`es_vkm_channels` в SQLite использовалась только для ВКМ, вкладка UI
называлась «Каналы ЭС».

**Решение от 2026-08-31:** `integration.Config.Points []PointMapping`
— список произвольной длины (тег параметра прибора → `ID_PP` в ЭС →
множитель), одинаково подходящий для ВКМ (4 записи: `ST`/`S`/`T`/`Pi`)
и Akron (1 запись: `V`). Таблица SQLite `es_vkm_channels` **переиспользована
как есть, без миграции схемы** — проверено напрямую по её `CREATE
TABLE`: `(device_id, tag, es_channel_id, factor)`, никакой привязки к
типу прибора там никогда не было, только имя таблицы осталось
историческим. UI-вкладка объединена и переименована в «Точки ЭС»,
показывает разное число строк по типу выбранного прибора.

**Важный нюанс, найденный оператором 2026-09-02:** при обобщении кода
`TimeShiftMinutes` (сдвиг метки времени при записи, подобранный
эмпирически для ВКМ, см. раздел 3.3) был **механически** применён и к
Akron без всяких оснований — это было ошибкой обобщения, исправлено:
сдвиг применяется **только** в `collectVKMReadings`, НЕ в
`collectAkronReadings`.

### 2.5. Параллельный опрос приборов вместо последовательного

Исходная реализация `internal/poller` была **намеренно однопоточной**
(проектный принцип «простейшая заведомо корректная версия» —
см. doc-комментарий в старой версии файла) — одно задание из очереди
планировщика обрабатывалось за раз, строго по очереди.

**Решение от 2026-08-31 (прямой запрос оператора, готовясь к росту до
~50 приборов):** каждое задание тика запускается в своей горутине,
защита от двойного опроса ОДНОГО прибора — через мьютекс на конкретный
`deviceID` (`sync.Map`), а не общий мьютекс на всех. `drain()`
по-прежнему дожидается всего пакета тика целиком через `WaitGroup`
(контракт для тестов не изменился), но внутри пакета работа идёт
параллельно.

Архитектурно проверено (см. раздел 3.4) на два риска — оба сняты:
переупорядочивание архивных заданий физически невозможно (планировщик
не выдаёт два задания одного вида на прибор в одном тике); зависание
одного прибора ограничено таймаутом транспорта и не блокирует другие
приборы (при последовательной версии зависшие приборы давали Бы сумму
таймаутов, при параллельной — максимум один таймаут на весь пакет).

### 2.6. Служба Windows как способ запуска — добавлена, но признана ненадёжной

**Решение от 2026-08-30:** добавлена поддержка `mbgw.exe
install-service` + правильный протокол взаимодействия со службами
Windows (`golang.org/x/sys/windows/svc`), включая обязательный
дескриптор безопасности для мьютекса единственного экземпляра
(`Global\mbgw_single_instance`, SDDL `D:(A;;GA;;;WD)`) — без него
`CreateMutex` падал с `Access is denied` при попытке одного
экземпляра (запущенного вручную, в сессии оператора) проверить, не
запущен ли уже другой (запущенный службой, в изолированной Session 0
под LocalSystem).

**Найдена, но НЕ исправлена (2026-08-30/31, живой инцидент в проде,
см. раздел 7):** после `sc start` служба показывает `STATE: RUNNING`,
но реальная работа (опрос, сбор архива, запись лога) иногда молча
останавливается вскоре после старта. Причина не найдена. **До
исправления рекомендуемый способ запуска — ручной** (`mbgw.exe
server` в открытой консоли) или через Планировщик заданий Windows
(`schtasks`, обходит протокол службы стороной).

### 2.7. Защита от двойного запуска процесса

**Решение от 2026-08-30 (прямой запрос оператора):** именованный
Windows-мьютекс `Global\mbgw_single_instance`
(`cmd/mbgw/single_instance_windows.go`) — до старта любой полезной
работы. При ошибке проверки (не при подтверждённом конфликте, а именно
при сбое самой проверки) выбран **строгий отказ в запуске**, а не
продолжение без защиты — обоснование: система пишет в финансово
значимую базу учёта, видимый простой безопаснее невидимой порчи
данных двумя параллельными процессами.

### 2.8. Ротация лог-файла

**Решение от 2026-08-29 (прямой запрос оператора, лог рос
неограниченно):** `cmd/mbgw/rotating_log.go` — простой `io.Writer` с
ротацией по размеру (20 МБ на файл, 10 архивов), без сторонних
библиотек (офлайн-сборка).

### 2.9. Кольцевой буфер лога в памяти + вкладка «Лог» в UI

**Решение от 2026-08-30 (прямой запрос оператора):** `internal/logbuf`
— третий получатель наравне с stdout и файлом, отдаёт последние ~5000
строк через `GET /api/log`. UI-вкладка обновляется раз в 2 секунды,
новые строки сверху (не снизу — решение от 2026-08-30, чтобы не
требовалась прокрутка).

**Доработка от 2026-09-02:** добавлена цветовая индикация активности
приборов — каждому прибору устойчивый цвет по хешу ID, полоска
индикаторов над логом должна вспыхивать при новых записях об этом
приборе.

**Живой баг подтверждён 2026-09-03:** индикация фактически не срабатывает:
реальные строки Go-лога начинаются с timestamp, а JS ищет `[device]`
только в начале строки. Поэтому не работают ни вспышки индикаторов, ни
окраска строк. Исправление запланировано в P1.8.

## 3. Факты, подтверждённые эмпирически в процессе разработки

Раздел содержит только то, что было **проверено на живых данных**, а
не выведено теоретически. Каждый пункт — с датой находки и способом
проверки, чтобы при сомнении можно было повторить проверку тем же
методом, а не поверить на слово.

### 3.1. Структура таблицы `PointMains` в БД ЭС (`CSD_Astrakhan`, схема `dbo`)

Проверено напрямую в SSMS 2026-08-31:

```sql
SELECT COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = 'dbo' AND TABLE_NAME = 'PointMains'
ORDER BY ORDINAL_POSITION;
```

Результат:

| Колонка | Тип | Nullable |
|---|---|---|
| `ID_PP` | int | NO |
| `DT` | datetime | NO |
| `Val` | float | NO |
| `State` | int | YES |

Пример живых строк (`SELECT TOP 5 * FROM dbo.PointMains WITH (NOLOCK)`
— **обязательно** с `NOLOCK`, без него запрос на этой таблице реально
подвесил интерфейс SSMS оператору на живом проде, 2026-09-02 —
таблица огромная, `ORDER BY DT DESC` без подходящего индекса вызывает
дорогую сортировку):

```
ID_PP   DT                       Val       State
155744  2010-01-01 14:30:00.000  0,1204    0
```

**Важно на будущее:** таблица `PointMains` разделяется между ВСЕМИ
точками учёта всей системы ЭС, не только нашими приборами — это
огромная общая таблица, любой запрос без узкого `WHERE ID_PP = ...`
или явного `TOP N` без `ORDER BY` рискует создать заметную нагрузку на
прод-базу заказчика.

### 3.2. Таблица `es_vkm_channels` (SQLite, локальная) физически не привязана к типу прибора

Проверено чтением `CREATE TABLE` (2026-08-31):

```sql
CREATE TABLE IF NOT EXISTS es_vkm_channels (
    device_id     TEXT NOT NULL,
    tag           TEXT NOT NULL,           -- 'ST' | 'S' | 'T' | 'Pi' | 'V' (Akron)
    es_channel_id INTEGER NOT NULL,
    factor        REAL NOT NULL DEFAULT 1.0,
    PRIMARY KEY (device_id, tag)
);
```

Никакой ссылки на `kind`/`device_type`, никакого `CHECK`-ограничения —
таблица годится для ЛЮБОГО типа прибора без миграции. Это подтверждено
фактом, а не предположением, ДО того, как таблица была переиспользована
для Akron (раздел 2.4) — минимизировало риск на переносе.

### 3.3. Эпоха секундного формата поля `Time=` у ВКМ-360

Прибор ВКМ-360 отдаёт архивную метку конца периода в одном из двух
форматов: обычная дата (`28/07/26 15:30:00`) или **секундный формат**
(`841444200сек` — число секунд от некой опорной точки). Опорная точка
эмпирически подобрана и **дважды перепроверена** после того, как
первая попытка оказалась ошибочной:

- **Первая (ошибочная) попытка** (2026-08-30): опорная дата задавалась
  напрямую через календарь 1999 года
  (`time.Date(1999, 12, 31, 0, 30, 0, 0, time.Local)`) — на живом
  сервере дала систематическую ошибку ровно `+1800` сек (один
  получасовой период) у обоих приборов ВКМ. Причина: Go резолвит
  часовой пояс ДЛЯ ДАТЫ 1999 ГОДА по историческим правилам, которые
  на сервере заказчика отличались от сегодняшних.
- **Вторая (тоже ошибочная) попытка** (2026-08-30, тот же день):
  переход на вычисление через сегодняшнюю дату
  (`time.Date(2026, 8, 29, 22, 30, 0, 0, time.Local).Add(-841442400 *
  time.Second)`) устранил проблему с историческим часовым поясом, НО
  само число `841442400` было **ошибочно считано с искажённого
  скриншота консоли** — сдвинуто на ровно один период от истинного.
  Ошибка `+1800` сек сохранилась.
- **Финальное, подтверждённое значение** (2026-08-31): перепроверено
  по **цепочке из 5+ идущих подряд периодов** архива `boylernaya_par`
  — где каждый следующий `START` в точности равен предыдущему `END`
  (это исключает ошибку чтения ОДНОЙ отдельной строки, в отличие от
  единичного примера):

  ```
  период 29.08.2026 16:30 -> сырой конец периода 841422600
  период 29.08.2026 17:00 -> 841424400   (шаг +1800)
  период 29.08.2026 17:30 -> 841426200
  ...
  период 29.08.2026 22:30 -> 841444200   (НЕ 841442400!)
  ```

  Итоговый код:
  ```go
  var vkmRawSecondsEpoch = time.Date(2026, 8, 29, 22, 30, 0, 0, time.Local).
      Add(-841444200 * time.Second)
  ```

  Проверено на 3 независимых точках цепочки одновременно, без единого
  расхождения. **Важно: найденная эпоха подтверждена именно этой цепочкой
  архивных значений, а не показателем `+0 сек` на dashboard.** 2026-09-03
  установлено, что dashboard сравнивал архивную метку с границей
  запрошенного периода и поэтому не измерял реальный wall-clock прибора.
  Следовательно, прежний `+0 сек` нельзя использовать как доказательство
  точности часов прибора или отсутствия дрейфа (см. P0.3).

  **Урок методологии** (см. также раздел 4): единичный пример,
  считанный с одного скриншота консоли, недостаточно надёжен для
  вывода эмпирической константы — нужна цепочка из нескольких
  независимых, взаимно проверяющих друг друга точек.

### 3.4. Архитектура опроса: подтверждено, что параллелизация безопасна

Проверено чтением `internal/scheduler/scheduler.go` (2026-08-31):
планировщик двигает `nextCurrentDue`/`nextArchiveDue` СРАЗУ при
постановке задания в очередь — физически не может поставить ДВА
задания одного вида для одного прибора в одном тике. Значит
переупорядочивание архивных заданий при параллельном диспетчере
(раздел 2.5) невозможно в принципе, а не «маловероятно».

Проверено чтением `internal/transport/{tcp,serial}.go`: оба транспорта
используют явные `SetReadDeadline`/`SetWriteDeadline`
(`ResponseTimeout`, по умолчанию 2 сек в тестах) — зависший прибор не
может блокировать процесс дольше своего таймаута.

### 3.5. Ловушка PowerShell: `sc` — алиас `Set-Content`, не вызов `sc.exe`

Подтверждено дважды живьём (2026-08-30): команда `sc start
mbgw_service` в PowerShell молча создавала файл с именем `start`
(содержимое — `mbgw_service`) вместо запуска службы, без единой
ошибки. Причина — встроенный алиас PowerShell. Решение: **всегда**
полный путь `C:\Windows\System32\sc.exe`.

### 3.6. Дескриптор безопасности мьютекса обязателен для межсессионного доступа

Подтверждено живьём (2026-08-30): `CreateMutex(nil, ...)` с
дескриптором безопасности по умолчанию НЕ даёт доступа процессу,
запущенному вручную (сессия оператора), к мьютексу, созданному
службой (LocalSystem, изолированная Session 0) — падает с `Access is
denied`. Решение — явный SDDL `D:(A;;GA;;;WD)` (см. раздел 2.7).

### 3.7. Полная (не уменьшенная) глубина сдвига дозабора для es-sync

Подтверждено живьём (2026-08-27): при окне поиска 168 часов (7 суток)
принудительный переопрос за месяц завершался успешно локально, но
данные месячной давности не попадали в ЭС — обычный цикл синхронизации
физически не заглядывал так далеко назад. Решение: окно увеличено до
2160 часов (90 суток) — не создаёт лишних записей (проверка на
существование точки в ЭС остаётся той же), просто реально проверяет
более глубокую историю.

### 3.8. `TimeShiftMinutes` подобран ТОЛЬКО для ВКМ, неверно для Akron без отдельной проверки

Значение `-90` минут (наблюдавшееся смещение ~1.5 часа) подобрано
СРАВНЕНИЕМ часа в ЭС с часом в родной программе прибора — то есть
методом, специфичным для того, КАК именно ВКМ раскладывает свои прямые
записи в старой таблице. При обобщении кода под Akron (раздел 2.4) это
значение было **механически, без проверки** применено и к Akron —
ошибка, исправленная 2026-09-02 (см. раздел 2.4, последний абзац).
Если для Akron когда-либо понадобится сдвиг — его нужно подбирать **тем
же методом** заново, отдельно, не переиспользуя число `-90`.

### 3.9. [ПОДТВЕРЖДЕНО И ИСПРАВЛЕНО В КОДЕ] Akron: `archive_hourly.value` для `V` — накопительный счётчик

**Подтверждено 2026-09-02/03 чтением кода и живыми данными.** `archive_hourly`
для Akron хранит сырое накопительное показание `V` на границе часа, а не
готовый расход за час. Вкладка «Архив» уже учитывала это через разницу
соседних показаний, но `collectAkronReadings` при прямой записи в ЭС брал
`row.Value` напрямую. Поэтому в `PointMains` попало значение порядка
`2 238 244` вместо часового объёма.

Исправление закоммичено в `52512ee`: для `V` загружается предыдущая
часовая точка и в ЭС отправляется только дельта соседних снимков. При дыре
между часами или уменьшении счётчика точка не отправляется. Добавлены
регрессионные тесты на `2238000 -> 2238244 -> 2238374`, ожидаемые часовые
дельты `244` и `130`, а также тест запрета схлопывания двухчасового разрыва
в одну часовую точку.

**Прод-подтверждение ещё не выполнено:** первая попытка выкладки `52512ee`
сорвалась из-за отдельного инцидента запуска бинарника на Windows Server
2008 R2 (`Exception 0xc0000005` внутри runtime). Точный toolchain и
происхождение именно упавшего файла через `go version -m` не были
зафиксированы, поэтому причина падения пока НЕ считается установленной.
После введения fail-closed build/deploy-проверки сначала проверить одну
часовую точку Akron, затем исправить уже испорченные строки ЭС.

## 4. Правила совместной работы в этом формате (модель + оператор-посредник в терминале)

Модель (Claude) не имеет прямого доступа к сети заказчика, серверу или
приборам. Весь код и все команды передаются оператору текстом, тот
выполняет их в PowerShell на реальной машине и присылает результат
обратно. Правила ниже сложились эмпирически, каждое — по следам
реальной ошибки, допущенной в процессе разработки.

### 4.1. Никогда не гадать по памяти о содержимом файла или API — сверяться с реальным кодом

Если модель не уверена в точной сигнатуре функции, структуре таблицы
или содержимом файла — **запросить его через `Get-Content`/`Select-
String` заново**, а не полагаться на память из более ранней части
разговора (код меняется, память может устареть или изначально быть
неточной). Правило родилось из нескольких реальных инцидентов, где
неверное предположение о структуре стоило лишнего раунда правок
(например, находка эпохи ВКМ — раздел 3.3 — потребовала перепроверки
именно потому, что первая попытка опиралась на неточно прочитанный
пример).

### 4.2. Перед любой отправкой файла оператору — механическая проверка целостности

Для каждого изменённого `.go`-файла — счётчик баланса фигурных/круглых
скобок (простой скрипт, игнорирующий скобки внутри строк/комментариев)
**до** того, как файл уйдёт оператору. Не заменяет компиляцию (её
делает оператор через `go build`), но ловит грубые ошибки редактирования
раньше, экономя раунд.

### 4.3. Кодировка и переносы строк — источник постоянных проблем, требует явной проверки

- **Скриншоты консоли PowerShell**, присылаемые оператором, часто
  показывают кириллицу как испорченную двойным перекодированием
  (`cp866`/`cp1251` → UTF-8). Расшифровка: попытаться
  `text.encode('cp866').decode('utf-8')`, при неудаче —
  `text.encode('cp1251').decode('utf-8')`.
- **Файлы, создаваемые моделью** (в т.ч. большой строковый литерал в
  `api_admin_ui.go`), должны заканчиваться на `\r\n` — Блокнот на
  старом Windows-сервере (в т.ч. на проде) не понимает одиночный `\n`,
  весь текст слипается в одну строку. Инструмент создания файлов по
  умолчанию пишет `\n` — после каждого создания/правки такого файла
  нужна явная нормализация (`replace(b'\r\n', b'\n').replace(b'\n',
  b'\r\n')`) и повторная проверка счётчиком `\r\n`/`\n`-only.
- Файлы Go-исходников, попавшие в git с `\n` (например, при первом
  создании), не требуют принудительной нормализации перед коммитом —
  `core.autocrlf` в этом репозитории сам приводит их к `\r\n` при
  checkout; проверено эмпирически (см. инцидент с `DEPLOY.txt`,
  раздел 6).

### 4.4. Перед каждым коммитом — обязательная сверка `git diff`, не слепой `git add`

Оператор присылает вывод `git diff <файл> | Out-File -Encoding utf8
diff.txt`, модель расшифровывает (см. 4.3) и **читает дифф целиком**
перед тем, как дать команду `git add`/`commit`. Правило родилось из
необходимости ловить случайные лишние правки (например, непреднамеренно
задетые несвязанные строки при поиске-замене) до того, как они попадут
в историю репозитория.

### 4.5. Один логический шаг — один явный раунд «правка → компиляция → дифф → коммит»

Не копить много некоммиченных изменений через несколько раундов
работы — иначе легко потерять из виду, что именно уже закоммичено, а
что всё ещё висит локально (реальный инцидент 2026-09-02: два готовых
и уже протестированных фикса — SDDL-дескриптор мьютекса и снятие
сдвига времени с Akron — остались не закоммиченными несколько раундов
подряд, обнаружены только по `git status` случайно).

### 4.6. Перед реализацией крупной или рискованной задачи — явный план и уточняющие вопросы, а не немедленный код

Для задач, затрагивающих финансово значимые данные (запись в БД
заказчика) или архитектуру нескольких файлов сразу — сначала
разведка (чтение реального кода/схемы), затем краткий план,
согласование неочевидных развилок с оператором, и только потом код.
Для мелких точечных правок — прямое действие без лишних вопросов
(баланс между «спросить» и «сделать» — оператор явно требовал не
разводить чрезмерную осторожность на пустом месте).

### 4.7. UI-кнопки/интерактивные виджеты (`ask_user_input_v0`) не работают в этом канале передачи

Обнаружено 2026-09-01/02 (оператором явно указано): интерактивные
кнопки выбора, генерируемые инструментом уточняющих вопросов, не
отображаются оператору в используемом им интерфейсе. **Уточняющие
вопросы — только простым текстом.**

### 4.8. Инструкции по эксплуатации — обычный `.txt`, не `.md`

На сервере заказчика нет удобного просмотрщика Markdown — только
Блокнот. Документ для оператора (`docs/DEPLOY.txt`) оформляется как
простой текст с ASCII-разделителями разделов, без `#`/`` ``` ``/
таблиц в markdown-синтаксисе. (Этот документ, `PROJECT_BACKLOG.md`, —
markdown, потому что читается разработчиком/моделью через GitHub, не
оператором через Блокнот на проде.)

### 4.9. Никогда не предполагать серьёзность бага по формальному статусу («RUNNING»)

Инцидент 2026-08-30/31 (служба Windows) научил: формальный статус
(«процесс запущен», «STATE: RUNNING») не гарантирует, что система
реально работает. Единственная надёжная проверка — свежесть данных
(время последней строки лога, время последнего собранного периода
архива), не факт существования процесса.

## 5. Окружения

### 5.1. Разработка (dev-машина)

- Путь репозитория: `C:\mbgw-devkit\mbgw`
- ОС: Windows (та же машина, что и прод, либо аналогичная — на момент
  последней проверки подтверждено, что dev и прод — **один и тот же
  компьютер**, просто разные окна PowerShell; полагаться на это не
  стоит без явной проверки при смене инфраструктуры)
- Go-тулчейн: **`go1.20.14`** (вызывается явно этим именем, не просто
  `go`, — на машине может быть несколько версий). **Почему именно
  1.20.x, не новее** (см. `FINAL_TRD.md` §2, §6 — источник этого
  требования, не мой домысел): целевая платформа — **Windows Server
  2008 R2**. Начиная с Go 1.21 минимальная поддерживаемая версия
  Windows была поднята производителем Go — начиная с этой версии
  собранный бинарник физически не запустился бы на сервере заказчика.
  Go 1.20.x — последняя ветка, ещё поддерживающая эту старую ОС.
  **Практическое следствие** (подтверждено живьём, 2026-08-30 —
  раздел 5.1 ниже, инцидент с `golang.org/x/sys`): при добавлении
  ЛЮБОЙ новой зависимости нужно следить, чтобы САМА зависимость тоже не
  требовала более новый Go, чем 1.20.x, иначе сборка ЭТИМ тулчейном
  откажет с ошибкой вида `cannot compile Go 1.25 code`.
- **Почему сборка офлайн (`-mod=vendor`, `GOPROXY=off`)**: см.
  `FINAL_TRD.md` §1 — целевая сеть заказчика **изолированная, без
  интернета**. Не стилистическое предпочтение, а жёсткое требование
  среды эксплуатации.
- **Почему `CGO_ENABLED=0`, единый статический бинарник**: прямое
  следствие того же требования — ни один DLL/рантайм не должен
  доустанавливаться на сервере заказчика отдельно; весь перенос
  версии на прод в этом проекте буквально сводится к копированию
  ОДНОГО файла `mbgw.exe` (см. раздел 5.4/`DEPLOY.txt`) — так и
  оставалось верным весь ход разработки, ни разу не потребовалось
  ничего, кроме `Copy-Item`.
- Сборка (обязательно так, не иначе):
  ```powershell
  cd C:\mbgw-devkit\mbgw
  $env:GOOS="windows"; $env:GOARCH="amd64"
  go1.20.14 build -mod=vendor -o bin/mbgw.exe ./cmd/mbgw
  certutil -hashfile C:\mbgw-devkit\mbgw\bin\mbgw.exe SHA256
  ```
- `-mod=vendor` обязателен — сборка офлайн, зависимости в `vendor/`.
- Добавление новой зависимости — ТОЛЬКО через `go1.20.14 mod tidy` (не
  `go get pkg@latest`, который может подтянуть версию, требующую
  более новый Go, чем `1.20.14` — реальный инцидент 2026-08-30,
  `golang.org/x/sys/windows/svc`) и обязательно `go1.20.14 mod vendor`
  после. Проверять `git status`/`go.mod` diff на предмет каскадных
  изменений версий НЕСВЯЗАННЫХ пакетов после `mod tidy` — если такие
  появились, разбираться, а не коммитить бездумно.
- Проверка перед каждым коммитом (обязательная тройка):
  ```powershell
  go1.20.14 vet ./...
  go1.20.14 test -mod=vendor ./...
  go1.20.14 build ./...
  ```

  вторичный источник при восстановлении хронологии.
- Временные diff-файлы (`diff_*.txt`), создаваемые в рабочей копии для
  передачи модели, **не коммитятся** — удаляются командой `Remove-Item`
  после того, как в них больше нет нужды.

### 5.3. Тестовое окружение

- `go1.20.14 test -mod=vendor ./...` — покрывает все пакеты с
  тестами; пакеты без тестов (`[no test files]`) — это нормально для
  части `cmd/`, `tools/`, тонких обвязочных пакетов.
- Юнит-тесты не требуют реального оборудования — используют
  симуляторы/`countingClient`-моки (см. `internal/poller/poller_test.go`

  опроса»).
- Живая проверка на реальном оборудовании заказчика — только через
  оператора, руками, после деплоя; не автоматизирована и не может быть

## 9. План стабилизации ядра после инцидентов 2026-09-02/03

Этот раздел — актуальная очередь работ поверх исходного
`IMPLEMENTATION_BACKLOG.md`. Каждый пункт выполняется отдельным логическим
заходом по правилу раздела 4.5: разведка -> минимальная правка -> тесты ->

### P0.1. Fail-closed legacy-сборка для Windows Server 2008 R2

**Проблема.** 2026-09-03 после выкладки нового exe на Windows Server
2008 R2 зафиксировано падение `Exception 0xc0000005` внутри runtime.
По присланному скриншоту один из запусков `--help` также завершился
успешным выводом справки, поэтому воспроизводимость и точная причина
пока не установлены. Версия Go и identity именно упавшего файла не были
зафиксированы через `go version -m`/встроенный build metadata. Следовательно,
утверждать, что причиной точно был новый Go, нельзя. При этом целевой
production toolchain по действующим требованиям проекта однозначен:
Go 1.20.14.

**Сделать:**
- production/legacy build всегда вызывает именно `go1.20.14`, а не `go`;
- сборка прекращается, если `go1.20.14 version` не даёт ожидаемую ветку;
- после сборки автоматически проверять `go version -m`/эквивалент и SHA256;
- встроить в exe git commit, время сборки и версию Go, показывать их при
  старте и в `/admin`;
- привести `Makefile`, `DEPLOY.txt` и противоречащий этому `ADR-002` к
  одному фактическому правилу: прод Windows Server 2008 R2 = Go 1.20.14.

**DoD:** production-сборка создаётся только подтверждённым Go 1.20.14;
до выкладки автоматически фиксируются toolchain, commit и SHA256;
бинарник сам сообщает build metadata; smoke на целевой Windows проходит.

### P0.2. Прод-проверка исправления Akron -> ЭС

Фикс уже в `52512ee` (см. 3.9/7.1). После P0.1 собрать корректный legacy

### P0.3. Реальное расхождение часов прибора и сервера

**Новый подтверждённый баг 2026-09-03.** Текущий показатель на «Главной»
не измеряет текущие часы ВКМ. `collectVKMPeriod` сравнивает время конца
архивного периода, которое прибор вернул на наш запрос, с границей того
же периода, которую сервер сам запросил. Это проверяет соответствие
архивной метки запросу, но не реальный wall-clock прибора, поэтому может

### P0.4. Единая сериализация физического I/O на прибор

Проверить все пути к `Transport`: плановый current/archive/backfill,
ручной «Принудительный переопрос», диагностические операции. Один прибор
не должен иметь параллельные транзакции в один физический канал. Лок
должен покрывать целую транзакцию `Send -> Receive`, а не отдельные
половины обмена. Это приоритетнее дальнейших новых функций.

### P1.1. Стартовый backfill через очередь poller

Убрать блокирующий startup-backfill до `poller.Run()`. Использовать уже
существующий `scheduler.KindBackfill`, чтобы один медленный прибор не
задерживал запуск полезной работы остальных и чтобы backfill проходил
через ту же сериализацию I/O.

### P1.2. Инкрементальная обычная синхронизация с ЭС

Убрать перечитывание 90 суток и тысячи `PointExists()` каждую минуту.
Первый шаг — хранить последнюю подтверждённо синхронизированную метку на
пару `(device, point)` и читать обычным циклом только более новые данные.
`ForceResyncRange` остаётся отдельным полным проходом. Полноценный outbox
добавлять только если понадобится гарантированная поштучная доставка при
частичном сбое пачки.

### P1.3. Явная семантика `counter` / `interval`

Физический смысл значения не должен жить в UI или конкретном потребителе.
Для Akron `V` явно описать как накопительный счётчик и централизовать
преобразование `counter -> interval delta` в одном месте, чтобы UI,
обычная синхронизация и пересинхронизация использовали одну семантику.

### P1.4. Safety-барьер перед записью в ЭС

Перед `InsertPoint`/`UpdatePoint` добавить настраиваемую проверку
допустимого диапазона. Аномальная точка не пишется и логируется как
`[ES-SAFETY] REFUSED` с device/point/time/value/reason. Это второй барьер,
не замена правильной семантике данных.

### P1.5. ЭС недоступна при старте — worker не должен умирать навсегда

Начальный `Ping()` не должен завершать sync-goroutine безвозвратно.
Нужен retry/backoff с WARN; после восстановления ЭС worker продолжает
дозабор из локальной SQLite.

### P1.6. Health-monitor полезной работы

Отдельно показывать не только факт существования процесса, а heartbeat:
последний цикл poller, последний успешный current/archive по прибору,
последнюю успешную запись в ЭС, состояние SQLite. Формальный
`STATE: RUNNING` не считается доказательством работоспособности.

### P1.7. Preview + audit для принудительной пересинхронизации

Перед изменением `PointMains` показывать оператору диапазон, количество
insert/update, min/max и несколько первых `old -> new`. После явного
подтверждения выполнять запись и фиксировать audit: кто/когда/прибор/
диапазон/сколько строк. Это особенно важно для финансово значимой БД.
