## 0. Что это за документ и как им пользоваться

Это НЕ замена существующим проектным документам
(`FINAL_TRD.md`, `LLD.md`, `CONTRACTS.md`, `IMPLEMENTATION_BACKLOG.md`,
`TEST_STRATEGY.md`, `MOCK_DATA_SPEC.md`, `profile_schema.json`) — они
остаются источником истины для исходного технического задания и
контрактных файлов. Этот документ — **связующий слой поверх них**:

- показывает, где и почему **реальная реализация разошлась** с
  исходным ТЗ (см. раздел 1);
- фиксирует **конкретные архитектурные решения**, принятые в процессе
  работы над реальным заказом, которых не было (и не могло быть) в
  исходном ТЗ, писавшемся до знакомства с реальным заказчиком и его
  оборудованием (раздел 2);
- фиксирует **факты, подтверждённые эмпирически** в процессе разработки
  и эксплуатации — не гипотезы, а проверенные значения/поведения
  (раздел 3);
- фиксирует **правила совместной работы** в этом конкретном формате
  (терминал + человек-посредник без прямого доступа модели к серверу) —
  раздел 4;
- описывает **окружения** (разработка, git, тесты, прод) — раздел 5;
- даёт **хронологию по спринтам**, включая явное указание, на чём
  остановились прямо сейчас — раздел 6;
- фиксирует **известный технический долг** — раздел 7.

## 1. Отклонения реальной реализации от исходного ТЗ (`FINAL_TRD.md`)

Важно прочитать это ПЕРЕД `FINAL_TRD.md` — иначе можно принять
устаревшие пункты исходного ТЗ за актуальное состояние проекта.

`FINAL_TRD.md` писался как техническое задание на **абстрактный
многоприборный MVP** для рынка АСКУЭ/АИИС КУЭ вообще — до появления
конкретного заказчика с конкретными приборами и конкретной системой
учёта (Энергосфера, `CSD_Astrakhan`). По мере работы с реальным
заказчиком проект прагматично отклонился от части исходных решений —
не из-за ошибки планирования, а потому что **реальные ограничения
заказчика оказались конкретнее и жёстче**, чем абстрактный MVP мог
предвидеть.

| Пункт FINAL_TRD | Что решено вместо этого | Почему |
|---|---|---|
| Web UI: TypeScript SPA, `go:embed web/dist` (§ FINAL_TRD п.2) | Admin UI — один Go-файл (`internal/web/api_admin_ui.go`) с HTML/CSS/ES5-JS как строковый литерал, отдаётся напрямую | Целевая площадка — старый Windows Server с Internet Explorer как единственным доступным браузером у оператора. Полноценный SPA-тулчейн (сборка TS, современный JS) избыточен и не нужен для одного узкоспециализированного admin-экрана; ES5 без async/await/fetch — осознанное ограничение под IE |
| REST API по OPENAPI.yaml, TLS обязателен (§3.4) | Простой `net/http`, без TLS, слушает `127.0.0.1:<порт>` | Единственный потребитель — сам оператор на этой же машине через браузер; сеть изолированная, заказчик не просил TLS. Может быть добавлено post-MVP, если периметр изменится |
| RBAC/роли/аутентификация (§3.4) | Отсутствует полностью — `/admin` открыт без логина | Тот же периметр — один оператор, один сервер, без сетевого доступа извне. Формально это осознанный риск, не забытая задача |
| PostgreSQL/TimescaleDB опционально (§2) | Только SQLite (`modernc.org/sqlite`), никогда не рассматривался Postgres всерьёз | Объём данных (единицы приборов, получасовые архивы) далёк от того, где потребовалась бы отдельная СУБД; упрощение эксплуатации важнее |
| Интеграция наружу: MQTT/gRPC/extDB — post-MVP (§3.2) | **extDB реализована в MVP и является ЕДИНСТВЕННЫМ работающим путём доставки данных в систему учёта** (`internal/integration/extdb.go`, `energosphere_sync.go`) | Родной драйвер Энергосферы (ЭС) для части каналов (тепло/давление ВКМ) отказался принимать данные независимо от их содержимого — проверено исчерпывающе (см. раздел 3). Прямая запись в БД ЭС — единственный подтверждённый рабочий канал, а не запасной вариант «на потом» |
| Единый абстрактный список из 4 приборов (ВКМ-360, ИВК-ТЭР, ТСРВ-024, Меркурий), профили равнозначны | Реально в проде эксплуатируются **ВКМ-360** и **Akron** (последнего в исходном списке 4 приборов не было вообще) | Заказчик пришёл с конкретным парком приборов, отличным от исходного планового списка. ИВК-ТЭР/ТСРВ-024/Меркурий остаются в кодовой базе как поддерживаемые профили, но не подтверждены на реальном оборудовании этого заказчика |
| Failover канала входит в MVP, failback выключен по умолчанию (§5) | Реализовано в общем виде через `internal/channel`, но НЕ упражнялось на реальном оборудовании этого заказчика — только один канал на прибор в проде | Формально код есть, но подтверждённого факта работы failover на реальном канале связи этого заказчика нет — см. технический долг (раздел 7) |
| Аудит изменений конфигурации — входит в MVP (§3.4) | Не реализовано | Заказчик не запрашивал; отложено, не забыто — см. технический долг |
| Разработка «без реальных приборов», только через симуляторы (§2) | Разработка и отладка **на реальных приборах заказчика**, удалённо через оператора-посредника (человек на месте выполняет команды в PowerShell, модель не имеет прямого доступа к сети/приборам/серверу) | Единственный практичный способ найти реальные проблемы (например, находка эпохи секундного формата Time= у ВКМ, структура PointMains в ЭС) — симулятор не мог бы вскрыть эти детали, они специфичны для КОНКРЕТНОГО экземпляра оборудования заказчика |

**Важный вывод из этой таблицы**, значимый для дальнейшей работы: этот
проект прошёл путь от «абстрактного мультиприборного MVP» к
«конкретному промышленному шлюзу для одного заказчика» — архитектурная
гибкость исходного профиль-ориентированного ядра (Protocol HAL,
`internal/profile`) сохранена и оправдала себя (новый прибор Akron
добавился без изменения ядра), но периферийные решения (web UI, TLS,
RBAC, способ доставки в систему учёта) переопределены под реальность,
а не под первоначальный абстрактный план.

## 2. Архитектурные решения, принятые в процессе (не отражены в исходных LLD/CONTRACTS)

### 2.1. Единый режим запуска `mbgw server` вместо связки из отдельных команд

Первоначально предполагалась связка `run`/`serve`/`northbound`/
`es-sync` как отдельных процессов. В проде используется **только**
`mbgw server` — единый процесс, конфигурация целиком из SQLite БД
(devices, каналы ЭС, подключение к ЭС — всё редактируется через
`/admin`, ничего через YAML/текстовые конфиги вручную). Остальные
команды (`run`, `serve`, `es-sync` с текстовым конфигом) оставлены в
`main.go` для обратной совместимости/разработки, но не являются
рекомендуемым способом эксплуатации.

### 2.2. Прямая запись в БД ЭС вместо эмуляции прибора — для ОБОИХ типов приборов

Исходно (первая реализация): ВКМ — прямая запись в SQL Server ЭС;
Akron — эмуляция физического прибора по протоколу АКРОН-01-1, чтобы
родной драйвер ЭС подключался и забирал данные
(`internal/northbound/akron_live.go`).

**Решение от 2026-08-31:** оба типа приборов переведены на один механизм
прямой записи в `dbo.PointMains` через
`internal/integration/energosphere_sync.go`.

**Уточнение/зачистка 2026-09-04:** текущий production-путь
`mbgw server` больше не содержит вызов/функцию
`startAkronNorthboundForDevice`, импорт `internal/northbound` из
`cmd/mbgw/server.go` удалён. Следовательно, именно production `server`
больше не создаёт `<device>_akron_live.jsonl`. При этом пакет
`internal/northbound` и отдельные legacy-команды оставлены в дереве для
исторической совместимости/диагностики. Если файл `*_akron_live.jsonl`
после новой сборки всё ещё меняется на проде, это уже признак другого
legacy-процесса/команды или старого exe, а не текущего `mbgw server`.

Причина унификации: один путь доставки проще сопровождать и проверять;
логика преобразования данных теперь находится перед одной общей точкой
записи в ЭС.

### 2.3. Целевая таблица ЭС: `PointMains` (`ID_PP`) вместо `Mains` (`ID_Channel`)

**Решение от 2026-08-31 (прямой запрос оператора).** Заказчик указал
новую целевую таблицу в ЭС: `dbo.PointMains` со столбцами `ID_PP`
(int), `DT` (datetime), `Val` (float), `State` (int) — вместо ранее
использовавшейся `dbo.Mains` (`ID_Channel`/`MeasureDate`/`Value`/
`State`). Подтверждено напрямую в SSMS запросом к `PointMains` (см.
раздел 3 — точная структура).

`internal/integration/extdb.go`: тип переименован `MainsWriter` →
`PointMainsWriter`, все SQL-запросы переведены на новую таблицу и
колонки.

**Отдельная деталь подключения, тоже без объяснения причины «на
глаз» — зафиксирована прямо в коде** (`extdb.go`,
`OpenPointMainsWriter`): подключение к SQL Server ЭС идёт с
`encrypt=disable`. Причина — целевая база работает на **SQL Server
2008 R2**, версия которого старше, чем ожидания драйвера по
умолчанию для TLS-подключений (современный mssql-драйвер по умолчанию
пытается TLS, старый сервер этого не понимает — согласование
шифрования падает). Безопасно отключать здесь только потому, что
подключение остаётся в пределах `localhost`/изолированной сети
заказчика — не следует переносить эту настройку бездумно в проект
с другим периметром безопасности.

### 2.4. Обобщённая модель «точка ЭС» вместо VKM-специфичных «каналов»

Раньше сопоставление «параметр прибора → номер в ЭС» существовало
только для ВКМ (4 захардкоженных поля `ChanHeat`/`ChanMass`/
`ChanTemp`/`ChanPressure` в `integration.Config`), таблица
`es_vkm_channels` в SQLite использовалась только для ВКМ, вкладка UI
называлась «Каналы ЭС».

**Решение от 2026-08-31:** `integration.Config.Points []PointMapping`
— список произвольной длины (тег параметра прибора → `ID_PP` в ЭС →
множитель), одинаково подходящий для ВКМ (4 записи: `ST`/`S`/`T`/`Pi`)
и Akron (1 запись: `V`). Таблица SQLite `es_vkm_channels` **переиспользована
как есть, без миграции схемы** — проверено напрямую по её `CREATE
TABLE`: `(device_id, tag, es_channel_id, factor)`, никакой привязки к
типу прибора там никогда не было, только имя таблицы осталось
историческим. UI-вкладка объединена и переименована в «Точки ЭС»,
показывает разное число строк по типу выбранного прибора.

**Уточнение по `TimeShiftMinutes` (финальная проверка 2026-09-04).**
Промежуточное решение от 2026-09-02 «сдвиг только для ВКМ» оказалось
неполным. Живая сверка Akron с `PointMains` показала такой же фактический
сдвиг меток при прямой записи. Поэтому текущий код применяет
`TimeShiftMinutes` **к обоим типам приборов**.

Для Akron порядок теперь строго такой:

1. взять два соседних часовых снимка накопительного `V`;
2. вычислить часовую дельту только если шаг ровно 1 час и счётчик не
   уменьшился;
3. разделить часовую дельту пополам;
4. сформировать две получасовые точки с метками конца интервала
   `HH:30` и `HH+1:00`;
5. применить к обеим точкам `TimeShiftMinutes`.

Источник локального архива при этом фильтруется в его исходной временной
шкале; сдвиг относится именно к метке, записываемой в ЭС.

### 2.5. Параллельный опрос приборов вместо последовательного

Исходная реализация `internal/poller` была **намеренно однопоточной**
(проектный принцип «простейшая заведомо корректная версия» —
см. doc-комментарий в старой версии файла) — одно задание из очереди
планировщика обрабатывалось за раз, строго по очереди.

**Решение от 2026-08-31 (прямой запрос оператора, готовясь к росту до
~50 приборов):** каждое задание тика запускается в своей горутине,
защита от двойного опроса ОДНОГО прибора — через мьютекс на конкретный
`deviceID` (`sync.Map`), а не общий мьютекс на всех. `drain()`
по-прежнему дожидается всего пакета тика целиком через `WaitGroup`
(контракт для тестов не изменился), но внутри пакета работа идёт
параллельно.

Архитектурно проверено (см. раздел 3.4) на два риска — оба сняты:
переупорядочивание архивных заданий физически невозможно (планировщик
не выдаёт два задания одного вида на прибор в одном тике); зависание
одного прибора ограничено таймаутом транспорта и не блокирует другие
приборы (при последовательной версии зависшие приборы давали Бы сумму
таймаутов, при параллельной — максимум один таймаут на весь пакет).

### 2.6. Служба Windows как способ запуска — добавлена, но признана ненадёжной

**Решение от 2026-08-30:** добавлена поддержка `mbgw.exe
install-service` + правильный протокол взаимодействия со службами
Windows (`golang.org/x/sys/windows/svc`), включая обязательный
дескриптор безопасности для мьютекса единственного экземпляра
(`Global\mbgw_single_instance`, SDDL `D:(A;;GA;;;WD)`) — без него
`CreateMutex` падал с `Access is denied` при попытке одного
экземпляра (запущенного вручную, в сессии оператора) проверить, не
запущен ли уже другой (запущенный службой, в изолированной Session 0
под LocalSystem).

**Найдена, но НЕ исправлена (2026-08-30/31, живой инцидент в проде,
см. раздел 7):** после `sc start` служба показывает `STATE: RUNNING`,
но реальная работа (опрос, сбор архива, запись лога) иногда молча
останавливается вскоре после старта. Причина не найдена. **До
исправления рекомендуемый способ запуска — ручной** (`mbgw.exe
server` в открытой консоли) или через Планировщик заданий Windows
(`schtasks`, обходит протокол службы стороной).

### 2.7. Защита от двойного запуска процесса

**Решение от 2026-08-30 (прямой запрос оператора):** именованный
Windows-мьютекс `Global\mbgw_single_instance`
(`cmd/mbgw/single_instance_windows.go`) — до старта любой полезной
работы. При ошибке проверки (не при подтверждённом конфликте, а именно
при сбое самой проверки) выбран **строгий отказ в запуске**, а не
продолжение без защиты — обоснование: система пишет в финансово
значимую базу учёта, видимый простой безопаснее невидимой порчи
данных двумя параллельными процессами.

### 2.8. Ротация лог-файла

**Решение от 2026-08-29 (прямой запрос оператора, лог рос
неограниченно):** `cmd/mbgw/rotating_log.go` — простой `io.Writer` с
ротацией по размеру (20 МБ на файл, 10 архивов), без сторонних
библиотек (офлайн-сборка).

### 2.9. Кольцевой буфер лога в памяти + вкладка «Лог» в UI

**Решение от 2026-08-30 (прямой запрос оператора):** `internal/logbuf`
— третий получатель наравне с stdout и файлом, отдаёт последние ~5000
строк через `GET /api/log`. UI-вкладка обновляется раз в 2 секунды,
новые строки сверху (не снизу — решение от 2026-08-30, чтобы не
требовалась прокрутка).

**Доработка от 2026-09-02:** добавлена цветовая индикация активности
приборов — каждому прибору устойчивый цвет по хешу ID, полоска
индикаторов над логом должна вспыхивать при новых записях об этом
приборе.

**Живой баг подтверждён 2026-09-03:** индикация фактически не срабатывает:
реальные строки Go-лога начинаются с timestamp, а JS ищет `[device]`
только в начале строки. Поэтому не работают ни вспышки индикаторов, ни
окраска строк. Исправление запланировано в P1.8.

### 2.10. Единый I/O-lock на физический канал

**Решение 2026-09-04, уточнено 2026-09-05 после внешнего ревью.**
`internal/pollcore` использует общий lock-key для сериализации полного
физического обмена (`NewWithLockKey`/`LockKey`).

Первоначально ключом был `deviceID`. Это корректно для обычного
`modbus_tcp`, но недостаточно для RS-485: два разных прибора на одном
`COM101` имеют разные `deviceID`, хотя физически делят одну линию и не
могут говорить одновременно.

Текущий контракт ключа:

- `rtu_serial` -> физический COM-порт (`COM101`, `COM105`, ...);
- `tcp_serial` -> адрес конвертера `host:port`, за которым находится
  общая последовательная линия;
- обычный `modbus_tcp` -> отдельный ключ прибора, так как это независимое
  TCP-соединение к самому устройству.

Один и тот же вычисленный ключ используется и для session handshake, и
для `pollcore.Reader`. Лок покрывает целую Modbus-транзакцию, включая
retry. Добавлены регрессионные тесты: два разных прибора на одном COM
обязаны получить общий mutex; разные COM — разные mutex; `modbus_tcp`
остаётся раздельным по приборам.

Это защита **физического канала**. Она не заменяет device-level lease,
который сериализует многошаговые логические операции одного прибора
(см. 2.16).

### 2.11. Startup-backfill через scheduler/poller, а не блокирующий вызов

**Решение 2026-09-04.** `registerOneDevice` больше не вызывает
`BackfillArchives` синхронно до регистрации прибора. После
`RegisterWithArchiveAnchor` стартовый дозабор ставится через
`scheduler.KindBackfill`.

Индивидуальный `BackfillMaxDepthHours` хранится в `device.Device`, чтобы
queued backfill не терял настройку конкретного прибора. Медленный
startup-backfill больше не задерживает регистрацию/полезную работу
прибора и проходит через ту же сериализацию I/O.

### 2.12. Подтверждённый cursor обычной синхронизации ЭС

**Решение 2026-09-04.** Добавлена SQLite-таблица `es_sync_cursor` с
ключом `(device_id, point_id)`. Обычный worker после первого backfill-окна
читает локальный архив начиная с подтверждённого cursor, а не перечитывает
90 суток каждую минуту.

Cursor двигается только после подтверждения конкретной точки
(`PointExists`, успешный insert или подтверждённый duplicate). Ошибка на
точке блокирует продвижение именно этой точки через дырку.
`ForceResyncRange` cursor намеренно не использует и не двигает.

### 2.13. Safety-барьер ЭС без выдуманных инженерных диапазонов

**Решение 2026-09-04.** Для каждой mapping-точки доступны nullable
`min_value`/`max_value`. `NULL` = соответствующая граница выключена.
Проверка идёт по итоговому значению после множителя и преобразования
counter/interval непосредственно перед `InsertPoint`/`UpdatePoint`.

`NaN`/`Inf` блокируются всегда. Никаких числовых пределов по умолчанию
код не придумывает. Настройки доступны на вкладке «Точки ЭС».

### 2.14. Health-monitor полезной работы

**Решение 2026-09-04.** Новый `internal/health` хранит:
- последний цикл центрального poller;
- последний успешный current по прибору;
- последний успешный archive по прибору;
- последнюю успешную реальную запись в ЭС;
- результат периодического SQLite `Ping`.

Dashboard/API показывает эти значения отдельно от формального статуса
процесса/Windows Service. Это прямое следствие инцидента
`STATE: RUNNING`, когда полезная работа фактически отсутствовала.

### 2.15. ForceResync: явные preview/execute и durable audit

**Решение 2026-09-04.** Endpoint принудительной пересинхронизации требует
явное `action = preview|execute`; отсутствие action больше не может
случайно запустить запись.

UI выполняет `preview -> показывает counts -> confirm -> execute`.
Preview использует тот же источник данных и safety-проверку, но не
вызывает `InsertPoint`/`UpdatePoint`.

SQLite-таблица `es_force_resync_audit` сохраняет `device/range/action`,
counts, `ok/error`, время события. Идентичность оператора пока не
фиксируется, потому что в текущем локальном `/admin` вообще нет
аутентификации/RBAC.

### 2.16. Device-level lease: одна логическая операция на прибор

**Решение 2026-09-05 после внешнего ревью.** Старый `LocalLease`
ключевался как `deviceID|leaseContext`, поэтому `current`, `archive`,
`backfill` и manual reload одного и того же прибора могли формально иметь
разные lease и выполняться одновременно на логическом уровне. Кроме того,
локальный lease автоматически истекал по TTL, что могло открыть прибор
для второй операции, пока первая реально ещё не закончилась.

Текущая семантика:

- ключ lease — **только `deviceID`**;
- `leaseContext` остаётся диагностической меткой для лога/ошибки, но не
  участвует в ключе;
- `Poll()` текущих значений также берёт тот же device-level lease;
- archive/backfill/manual reload/fencing конфликтуют с `Poll()` и между
  собой на всём приборе;
- локальный in-process lease не истекает сам по wall-clock TTL и
  освобождается только явным `release()`; при смерти процесса память
  lease исчезает вместе с процессом.

Физический I/O-lock и logical device lease решают разные задачи:
device lease не даёт вклиниться в многошаговую операцию **того же
прибора**, physical I/O-lock не даёт двум **разным приборам на общей
RS-485 линии** одновременно использовать канал.

### 2.17. Безопасная автокоррекция часов ВКМ-360

**Решение 2026-09-05, commit `251018c`.** На живом ВКМ подтверждены:

- текущее время — HR `1800..1805` (день/месяц/год/час/минута/секунда);
- коррекция времени — HR `1009`;
- кодирование команды: `correctionSeconds * 101`;
- live-проверка: команда `+8 сек` записала `808` и уменьшила фактический
  drift примерно с `-8 сек` до порядка `-1.5 сек`.

Для каждого ВКМ в SQLite/API/UI доступны:

1. допустимое абсолютное расхождение (deadband);
2. максимум одной коррекции (`0..99` сек — аппаратный предел);
3. максимум суммарного модуля коррекций за скользящие 24 часа.

Существующие приборы после миграции имеют нули, поэтому автокоррекция
по умолчанию выключена. Суточный лимит считается как сумма абсолютных
значений (`+20` и затем `-20` расходуют 40 секунд бюджета).

Для fail-safe учёта коррекция сначала резервируется в SQLite, и только
после этого отправляется HR1009. Если Modbus-запись не удалась или ответ
потерян, резерв остаётся до выхода из 24-часового окна: это консервативно,
но не позволяет физическим коррекциям превысить операторский лимит после
рестарта процесса.

### 2.18. Явная маршрутизация часов и безопасный `set-time` для VZLET/ИВК-ТЭР

**Решение 2026-09-07, commits `eeac5c2` и `b7c183c`.** Ранее
`updateTimeDrift()` различал Akron и фактически трактовал остальные
профили как ВКМ. Для ИВК-ТЭР это было неверно: профиль описывает
текущее время как `current_time` в IR `0x8000` (`uint32`, Unix epoch),
а ВКМ использует отдельный блок HR `1800..1805`.

Текущий контракт:

- Akron читает свой BCD wall-clock `0x10..0x13`;
- ВКМ-360 читает HR `1800..1805` и использует отдельную безопасную
  автокоррекцию HR1009;
- VZLET/ИВК-ТЭР читает профильную точку `current_time` и декодирует
  Unix timestamp с учётом `word_order_32`;
- неизвестный профиль больше не получает VKM-маршрут «по умолчанию»;
- write-only `time_set` не попадает в обычный poll.

Для ИВК-ТЭР запись времени остаётся явной командой `set-time`, потому
что HR `0x8000` доступен для записи только в Service/Setup mode.
Команда больше не использует жёсткий Modbus unit ID `1`: берёт реальный
адрес и параметры транспорта устройства, проверяет подтверждение записи
функции 16 и затем перечитывает часы. Автоматическую фоновую запись
часов ИВК-ТЭР в обычном `Poll()` намеренно не добавляли.

### 2.19. Консольный вывод не должен блокировать рабочие goroutine

**Решение подготовлено 2026-09-07 после полевого инцидента.** На старой
Windows Console оператор дважды наблюдал остановку полезной работы; на
скриншоте окно находилось в режиме выделения текста («Выбрать ... Windows
PowerShell»), а после действия с консолью накопившаяся работа продолжалась.
Текущий лог процесса использовал синхронный `io.MultiWriter` с `os.Stdout`,
поэтому блокирующая запись в консоль могла удержать goroutine, вызвавшую
`log.Printf`.

Подготовлен fail-soft путь: только консольная копия идёт через ограниченный
неблокирующий буфер; `mbgw_server.log` и внутренний `logbuf` остаются
синхронными. Перед разветвлением общий log-writer также переводит старые
служебные метки `[INFO]/[OK]/[WARN]/[ERROR]/[WEB]/[SAVE]/[poller]/[es-sync]`
в русские эквиваленты, поэтому консоль, файл и UI получают один русский
эксплуатационный лог. Если старая консоль перестала принимать вывод, разрешено
потерять только лишние строки на экране, но не остановить опрос и не потерять
файловый/web-лог. До production-smoke корень инцидента считать сильной
рабочей гипотезой, а не окончательно доказанным фактом.

### 2.20. Один SQLite Repo на production-процесс `mbgw server`

**Решение подготовлено 2026-09-07.** В production живьём получено
`database is locked (5) (SQLITE_BUSY)` при сохранении данных ВКМ во время
параллельной активности. Ревизия кода показала: основной `server` уже имел
свой `*sqliterepo.Repo`, но каждый worker синхронизации с ЭС дополнительно
открывал тот же SQLite-файл через отдельный `sqliterepo.New`. Даже при
`SetMaxOpenConns(1)` внутри каждого Repo это создаёт несколько независимых
connection pools, конкурирующих за SQLite writer-lock.

Production-путь переводится на общий уже открытый Repo процесса через
`RunEnergosphereSyncWithRepo`. Legacy CLI сохраняет вариант с открытием БД
по пути. Цель — убрать внутрипроцессную конкуренцию writer'ов, не отменяя
параллельный физический опрос разных приборов.

### 2.21. Принудительный переопрос архива не запускает Энергосферу

**Решение подготовлено 2026-09-07 по прямому требованию оператора.** Старый
web-workflow после каждых нескольких периодов и после завершения
принудительного переопроса вызывал trigger внеплановой синхронизации с ЭС.
Из-за этого нажатие кнопки во вкладке «Архив» порождало
`[синхронизация с ЭС] внеплановая синхронизация по запросу`, хотя оператор
не просил запись в ЭС.

Новый контракт жёсткий: **«Принудительный переопрос» = прибор -> локальная
БД МодбасШлюза**. Перезапись/пересинхронизация с `PointMains` выполняется
только отдельной явной операцией ЭС.

### 2.22. Runtime «Монитор опроса»

**Решение подготовлено 2026-09-07.** Для наблюдения за реальной
параллельностью и зависаниями добавляется отдельный runtime-монитор, а не
визуальная догадка по строкам лога. `internal/health` хранит активность
опроса, точное время начала, последний завершённый результат и ближайший
`next due`, который передаёт сам `scheduler`. Веб-переопрос архива, идущий
в обход poller, накладывается на монитор отдельно. Endpoint монитора читает
только память процесса и не обращается к SQLite каждую секунду.

### 2.23. Windows-служба владеет тем же server core, что и ручной запуск

**Решение 2026-09-08, находится в `main` начиная с `a28dd32`.** Старый путь
запускал `svc.Run` в отдельной goroutine, а жизненный цикл SCM и полезная
работа шлюза могли расходиться. Отсюда наблюдавшийся класс отказа
«`STATE: RUNNING`, а опроса нет».

Новый контракт: ручной `mbgw.exe server` и Windows-служба запускают одну
`runServerCore(ctx, onReady, runningAsService)`. В режиме службы context
принадлежит Service Handler. SCM остаётся в `StartPending` до фактического
старта poller; `Stop`/`Shutdown` переводят службу в `StopPending`, отменяют
общий context и ждут завершения активных per-device worker'ов. `Stopped`
сообщается только после возврата server core, чтобы новый процесс не мог
пересечься со старым на физической линии.

`install-service` сделан повторяемым: существующая служба обновляется без
ручного удаления. Настраиваются автоматический запуск и Recovery после
аварийного завершения (1, 2 и 5 минут). До live-smoke на старой Windows
Server это решение остаётся code-ready, а не production-confirmed.

### 2.24. Watchdog зависания не равен watchdog связи с приборами

**Решение 2026-09-08.** Защита следит за жизнью scheduler/poller и
продвижением очередей, а не за успешностью Modbus-ответов. Недоступность
прибора, таймаут или ошибка протокола сами по себе не являются причиной
перезапуска шлюза. Один зависший per-device worker даёт предупреждение, но
не перезапускает весь процесс, пока центральный цикл и другие приборы
продолжают работу. Глобальным считается остановившийся центральный цикл либо зависание всех
фактически зарегистрированных приборов одновременно. Отдельный критерий
по «просроченному nextDue» намеренно не используется: `scheduler.Tick()`
штатно переносит срок вперёд, а задания занятого прибора могут долго ждать
в его FIFO. Если сам `Tick`/`drainAsync` действительно зависнет, центральный
heartbeat перестанет обновляться; если зависнут per-device worker'ы — это
видно по отсутствию прогресса активной операции/очереди.

Таймаут задаётся в «Настройки» (2–120 минут, по умолчанию 10). При ручном
запуске/Планировщике подтверждённое зависание только поднимает красный
статус в UI и `/api/health` и пишет журнал — процесс не убивает себя. Если
процесс действительно запущен Windows-службой, критическая причина
фиксируется и процесс завершается ненулевым кодом; SCM Recovery поднимает
его снова.

Для диагностики используется отдельная SQLite БД `mbgw_service_log.db`
рядом с exe, а не `mbgw_server.db`: проблемы основной БД не должны лишать
оператора истории отказа. Критическая запись ограничена таймаутом 2 секунды,
чтобы watchdog не завис на самом журнале. Хранение — 30 дней; очистка при
старте и затем раз в сутки. Вкладка «Служба» показывает цветной русский
журнал и фильтры событий.

### 2.25. ИВК-ТЭР — полноценный профильный опрос без обхода сервисного режима

**Решение 2026-09-08, не live-confirmed.** Существующая стратегия
`mb_func65` умела декодировать запись ИВК-ТЭР, но штатный `PollArchives()`
не сохранял её поля в `archive_hourly`; регулярный путь также не был
оформлен как чтение вершины массива с последующим индексным дозабором.

Подготовлен путь: чтение паспортного `serial_number`, текущего расхода и
`current_time`; функция 65 с индексом 0 как вершиной часового архива;
сохранение числовых полей в `archive_hourly`; startup-backfill по индексам
в глубину; прогресс длительного дозабора учитывается watchdog. Во вкладке
«Архив» ИВК-ТЭР пока показывается только «Подробно (как хранится)»:
суточную/месячную агрегацию кодов состояния и остальных полей не выдумывать
до проверки реального прибора.

Коррекция времени остаётся только явной командой `set-time`: команда
сначала ищет конфигурацию прибора в production `mbgw_server.db` (legacy
`config.yaml` — fallback), отказывается писать при работающем основном
экземпляре шлюза и требует перевести ИВК-ТЭР в Service/Setup mode. После
функции 16 выполняется контрольное чтение. Автоматическую фоновую запись
HR `0x8000` не добавлять.

### 2.26. Время приборов показывается в «Мониторе опроса»

**Решение 2026-09-08.** Нижний блок истории коррекции времени с «Главной»
убирается из UI; backend-история не удаляется. В «Монитор опроса» добавлен
столбец «Время прибора»: фактическое расхождение и режим коррекции для
каждого типа. ВКМ показывает состояние автоматической коррекции и последнюю
реальную коррекцию; если она включена, но ни разу не срабатывала —
«Коррекция: включена, срабатываний не было». Akron — «Коррекция: не
реализована». ИВК-ТЭР — «Коррекция: только вручную, в сервисном режиме
прибора».

## 3. Факты, подтверждённые эмпирически в процессе разработки

Раздел содержит только то, что было **проверено на живых данных**, а
не выведено теоретически. Каждый пункт — с датой находки и способом
проверки, чтобы при сомнении можно было повторить проверку тем же
методом, а не поверить на слово.

### 3.1. Структура таблицы `PointMains` в БД ЭС (`CSD_Astrakhan`, схема `dbo`)

Проверено напрямую в SSMS 2026-08-31:

```sql
SELECT COLUMN_NAME, DATA_TYPE, IS_NULLABLE
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = 'dbo' AND TABLE_NAME = 'PointMains'
ORDER BY ORDINAL_POSITION;
```

Результат:

| Колонка | Тип | Nullable |
|---|---|---|
| `ID_PP` | int | NO |
| `DT` | datetime | NO |
| `Val` | float | NO |
| `State` | int | YES |

Пример живых строк (`SELECT TOP 5 * FROM dbo.PointMains WITH (NOLOCK)`
— **обязательно** с `NOLOCK`, без него запрос на этой таблице реально
подвесил интерфейс SSMS оператору на живом проде, 2026-09-02 —
таблица огромная, `ORDER BY DT DESC` без подходящего индекса вызывает
дорогую сортировку):

```
ID_PP   DT                       Val       State
155744  2010-01-01 14:30:00.000  0,1204    0
```

**Важно на будущее:** таблица `PointMains` разделяется между ВСЕМИ
точками учёта всей системы ЭС, не только нашими приборами — это
огромная общая таблица, любой запрос без узкого `WHERE ID_PP = ...`
или явного `TOP N` без `ORDER BY` рискует создать заметную нагрузку на
прод-базу заказчика.

### 3.2. Таблица `es_vkm_channels` (SQLite, локальная) физически не привязана к типу прибора

Проверено чтением `CREATE TABLE` (2026-08-31):

```sql
CREATE TABLE IF NOT EXISTS es_vkm_channels (
    device_id     TEXT NOT NULL,
    tag           TEXT NOT NULL,           -- 'ST' | 'S' | 'T' | 'Pi' | 'V' (Akron)
    es_channel_id INTEGER NOT NULL,
    factor        REAL NOT NULL DEFAULT 1.0,
    PRIMARY KEY (device_id, tag)
);
```

Никакой ссылки на `kind`/`device_type`, никакого `CHECK`-ограничения —
таблица годится для ЛЮБОГО типа прибора без миграции. Это подтверждено
фактом, а не предположением, ДО того, как таблица была переиспользована
для Akron (раздел 2.4) — минимизировало риск на переносе.

### 3.3. Эпоха секундного формата поля `Time=` у ВКМ-360

Прибор ВКМ-360 отдаёт архивную метку конца периода в одном из двух
форматов: обычная дата (`28/07/26 15:30:00`) или **секундный формат**
(`841444200сек` — число секунд от некой опорной точки). Опорная точка
эмпирически подобрана и **дважды перепроверена** после того, как
первая попытка оказалась ошибочной:

- **Первая (ошибочная) попытка** (2026-08-30): опорная дата задавалась
  напрямую через календарь 1999 года
  (`time.Date(1999, 12, 31, 0, 30, 0, 0, time.Local)`) — на живом
  сервере дала систематическую ошибку ровно `+1800` сек (один
  получасовой период) у обоих приборов ВКМ. Причина: Go резолвит
  часовой пояс ДЛЯ ДАТЫ 1999 ГОДА по историческим правилам, которые
  на сервере заказчика отличались от сегодняшних.
- **Вторая (тоже ошибочная) попытка** (2026-08-30, тот же день):
  переход на вычисление через сегодняшнюю дату
  (`time.Date(2026, 8, 29, 22, 30, 0, 0, time.Local).Add(-841442400 *
  time.Second)`) устранил проблему с историческим часовым поясом, НО
  само число `841442400` было **ошибочно считано с искажённого
  скриншота консоли** — сдвинуто на ровно один период от истинного.
  Ошибка `+1800` сек сохранилась.
- **Финальное, подтверждённое значение** (2026-08-31): перепроверено
  по **цепочке из 5+ идущих подряд периодов** архива `boylernaya_par`
  — где каждый следующий `START` в точности равен предыдущему `END`
  (это исключает ошибку чтения ОДНОЙ отдельной строки, в отличие от
  единичного примера):

  ```
  период 29.08.2026 16:30 -> сырой конец периода 841422600
  период 29.08.2026 17:00 -> 841424400   (шаг +1800)
  период 29.08.2026 17:30 -> 841426200
  ...
  период 29.08.2026 22:30 -> 841444200   (НЕ 841442400!)
  ```

  Итоговый код:
  ```go
  var vkmRawSecondsEpoch = time.Date(2026, 8, 29, 22, 30, 0, 0, time.Local).
      Add(-841444200 * time.Second)
  ```

  Проверено на 3 независимых точках цепочки одновременно, без единого
  расхождения. **Важно: найденная эпоха подтверждена именно этой цепочкой
  архивных значений, а не показателем `+0 сек` на dashboard.** 2026-09-03
  установлено, что dashboard сравнивал архивную метку с границей
  запрошенного периода и поэтому не измерял реальный wall-clock прибора.
  Следовательно, прежний `+0 сек` нельзя использовать как доказательство
  точности часов прибора или отсутствия дрейфа (см. P0.3).

  **Урок методологии** (см. также раздел 4): единичный пример,
  считанный с одного скриншота консоли, недостаточно надёжен для
  вывода эмпирической константы — нужна цепочка из нескольких
  независимых, взаимно проверяющих друг друга точек.

### 3.4. Архитектура опроса: подтверждено, что параллелизация безопасна

Проверено чтением `internal/scheduler/scheduler.go` (2026-08-31):
планировщик двигает `nextCurrentDue`/`nextArchiveDue` СРАЗУ при
постановке задания в очередь — физически не может поставить ДВА
задания одного вида для одного прибора в одном тике. Значит
переупорядочивание архивных заданий при параллельном диспетчере
(раздел 2.5) невозможно в принципе, а не «маловероятно».

Проверено чтением `internal/transport/{tcp,serial}.go`: оба транспорта
используют явные `SetReadDeadline`/`SetWriteDeadline`
(`ResponseTimeout`, по умолчанию 2 сек в тестах) — зависший прибор не
может блокировать процесс дольше своего таймаута.

### 3.5. Ловушка PowerShell: `sc` — алиас `Set-Content`, не вызов `sc.exe`

Подтверждено дважды живьём (2026-08-30): команда `sc start
mbgw_service` в PowerShell молча создавала файл с именем `start`
(содержимое — `mbgw_service`) вместо запуска службы, без единой
ошибки. Причина — встроенный алиас PowerShell. Решение: **всегда**
полный путь `C:\Windows\System32\sc.exe`.

### 3.6. Дескриптор безопасности мьютекса обязателен для межсессионного доступа

Подтверждено живьём (2026-08-30): `CreateMutex(nil, ...)` с
дескриптором безопасности по умолчанию НЕ даёт доступа процессу,
запущенному вручную (сессия оператора), к мьютексу, созданному
службой (LocalSystem, изолированная Session 0) — падает с `Access is
denied`. Решение — явный SDDL `D:(A;;GA;;;WD)` (см. раздел 2.7).

### 3.7. Полная (не уменьшенная) глубина сдвига дозабора для es-sync

Подтверждено живьём (2026-08-27): при окне поиска 168 часов (7 суток)
принудительный переопрос за месяц завершался успешно локально, но
данные месячной давности не попадали в ЭС — обычный цикл синхронизации
физически не заглядывал так далеко назад. Решение: окно увеличено до
2160 часов (90 суток) — не создаёт лишних записей (проверка на
существование точки в ЭС остаётся той же), просто реально проверяет
более глубокую историю.

### 3.8. `TimeShiftMinutes` нужен и ВКМ, и Akron при прямой записи в `PointMains`

Промежуточная запись этого документа от 2026-09-02 утверждала, что
`TimeShiftMinutes=-90` подтверждён только для ВКМ и должен быть снят с
Akron. **Это больше не актуально.**

Живая сверка 2026-09-04 показала: при текущем прямом пути Akron в
`PointMains` его временные метки также требуют настроенного общего
сдвига. Текущий код применяет `cfg.TimeShiftMinutes` и к ВКМ, и к Akron.

Для Akron сдвиг применяется не к сырому часовому totalizer, а уже к двум
получасовым endpoint-меткам после вычисления часовой дельты. Например,
логические точки `16:30`/`17:00` при `-90` записываются как
`15:00`/`15:30`.

Само значение `-90` остаётся **операторской настройкой**, а не
захардкоженной константой. При изменении конфигурации ЭС его нужно
перепроверять живой сверкой.

### 3.9. [ПОДТВЕРЖДЕНО В PROD 2026-09-07] Akron: `V` — totalizer -> часовая дельта -> две получасовки

`archive_hourly.value` для Akron `V` — накопительный счётчик на границе
часа. Старый путь прямой записи ошибочно мог отправить миллионы как
расход за период.

Первая исправленная версия (`52512ee`) ввела часовую дельту соседних
снимков и запрет схлопывания дыр. В ходе живой сверки 2026-09-04
уточнён **финальный контракт записи в ЭС**:

- соседние снимки должны отличаться ровно на `1h`;
- `delta = V(t) - V(t-1h)`;
- отрицательная дельта не отправляется;
- часовая дельта делится поровну на две получасовые точки;
- метки — конец получасовок: `t-30m` и `t`;
- затем к обеим применяется `TimeShiftMinutes`.

Пример: `V(17:00)-V(16:00)=244` -> `122` и `122`.
При `TimeShiftMinutes=-90` логические `16:30`/`17:00` уходят в ЭС как
`15:00`/`15:30`.

Для UI и ЭС теперь используется общий
`internal/interval.CounterDelta`, поэтому обе стороны одинаково
отбрасывают разрыв больше часа и уменьшение счётчика.

**Прод-подтверждение выполнено 2026-09-07.** Финальный Go 1.20.14
`mbgw.exe` перенесён на сервер; оператор проверил работу Akron на живой
системе и сообщил, что прибор работает без замечаний. Тем самым новый
путь сбора/передачи Akron считается прошедшим production smoke. Отдельная
массовая очистка старых ошибочных строк, если она понадобится, остаётся
самостоятельной осознанной операцией и не выполняется автоматически.

### 3.10. Текущее время приборов: Akron, ВКМ и профильный маршрут VZLET/ИВК-ТЭР

Для Akron подтверждён стандартный BCD-блок текущего времени
`0x10..0x13`. Код делает одну атомарную транзакцию, снимает серверное
время непосредственно до/после обмена и сравнивает часы прибора с
серединой RTT.

Для ВКМ-360 2026-09-05 живьём подтверждён read-only блок HR
`1800..1805`: день/месяц/год/час/минута/секунда. Код также читает все
шесть регистров одной транзакцией и считает drift относительно midpoint
RTT. Старое вычисление по архивной метке окончательно удалено как
некорректный суррогат текущих часов.

На том же реальном приборе подтверждена команда коррекции HR1009
(`seconds * 101`), после чего в основной код добавлена безопасная
автокоррекция с deadband, лимитом одного шага и rolling-24h budget
(см. 2.17).

С 2026-09-07 маршрут времени для VZLET/ИВК-ТЭР отделён от ВКМ:
`current_time` читается из профильной IR `0x8000` как `uint32` Unix
timestamp. Для установки используется профильная HR `0x8000` через
явную команду `set-time`; после записи выполняется контрольное чтение.
Это подтверждено кодом и регрессионными тестами, но **не считается
live-подтверждением на реальном ИВК-ТЭР** — профиль этого прибора всё
ещё не проверен в бою у текущего заказчика (см. 7.6).

### 3.11. Совместимость диагностического SQL со старым SQL Server

Живой диагностический запрос 2026-09-04 с литералом вида
`'20260901T15:00:00'` на старом SQL Server дал `Msg 241` (ошибка
преобразования даты/времени).

Для ручной диагностики на этом сервере использовать ODBC timestamp
escape:

`{ts 'YYYY-MM-DD HH:MM:SS'}`

либо обходиться без datetime-литерала через узкий `WHERE ID_PP=...`,
`TOP N` и безопасную сортировку. Это правило относится к диагностическим
командам SSMS и не меняет Go-код драйвера.

## 4. Правила совместной работы в этом формате (модель + оператор-посредник в терминале)

Модель (Claude) не имеет прямого доступа к сети заказчика, серверу или
приборам. Весь код и все команды передаются оператору текстом, тот
выполняет их в PowerShell на реальной машине и присылает результат
обратно. Правила ниже сложились эмпирически, каждое — по следам
реальной ошибки, допущенной в процессе разработки.

### 4.1. Никогда не гадать по памяти о содержимом файла или API — сверяться с реальным кодом

Если модель не уверена в точной сигнатуре функции, структуре таблицы
или содержимом файла — **запросить его через `Get-Content`/`Select-
String` заново**, а не полагаться на память из более ранней части
разговора (код меняется, память может устареть или изначально быть
неточной). Правило родилось из нескольких реальных инцидентов, где
неверное предположение о структуре стоило лишнего раунда правок
(например, находка эпохи ВКМ — раздел 3.3 — потребовала перепроверки
именно потому, что первая попытка опиралась на неточно прочитанный
пример).

### 4.2. Перед любой отправкой файла оператору — механическая проверка целостности

Для каждого изменённого `.go`-файла — счётчик баланса фигурных/круглых
скобок (простой скрипт, игнорирующий скобки внутри строк/комментариев)
**до** того, как файл уйдёт оператору. Не заменяет компиляцию (её
делает оператор через `go build`), но ловит грубые ошибки редактирования
раньше, экономя раунд.

### 4.3. Кодировка и переносы строк — источник постоянных проблем, политика зафиксирована в git

- **Скриншоты консоли PowerShell**, присылаемые оператором, часто
  показывают кириллицу как испорченную двойным перекодированием
  (`cp866`/`cp1251` -> UTF-8). Расшифровывать осторожно и при сомнении
  сверяться с исходным файлом, а не принимать mojibake за реальный текст.
- 2026-09-05 в корень репозитория добавлен `.gitattributes`, чтобы
  окончания строк перестали зависеть от локального `core.autocrlf`:
  исходники/конфиги/документация нормализуются как LF, Windows-скрипты
  (`.ps1/.bat/.cmd`) — как CRLF, бинарные типы помечены binary.
- Массовый `git add --renormalize .` в текущем stabilization-пакете
  **не выполняется**, чтобы не смешивать функциональные изменения с
  огромным механическим diff. Новая политика применяется к новым и
  реально изменяемым файлам.
- Перед отправкой оператору всё равно проверяется именно выдаваемый
  артефакт (см. 4.10); `.gitattributes` не заменяет эту проверку.

### 4.4. Перед каждым коммитом — обязательная сверка `git diff`, не слепой `git add`

Оператор присылает вывод `git diff <файл> | Out-File -Encoding utf8
diff.txt`, модель расшифровывает (см. 4.3) и **читает дифф целиком**
перед тем, как дать команду `git add`/`commit`. Правило родилось из
необходимости ловить случайные лишние правки (например, непреднамеренно
задетые несвязанные строки при поиске-замене) до того, как они попадут
в историю репозитория.

### 4.5. Логические коммиты, но только один финальный production exe на пакет

Для связанного stabilization-пакета допустимо накопить несколько
локальных взаимозависимых правок до общего зелёного теста. После этого
обязательно:

1. удалить временные файлы передачи;
2. прочитать полный `git diff`;
3. разделить изменения на понятные логические коммиты;
4. push;
5. собрать **один** финальный production exe.

Не переносить на production промежуточный exe после каждого маленького
шага — перенос/проверка бинарника на старом сервере дорогие и создают
лишний риск. При этом нельзя слепо коммитить всё одной кучей: история
git должна сохранять логические границы изменений.

### 4.6. Перед реализацией крупной или рискованной задачи — явный план и уточняющие вопросы, а не немедленный код

Для задач, затрагивающих финансово значимые данные (запись в БД
заказчика) или архитектуру нескольких файлов сразу — сначала
разведка (чтение реального кода/схемы), затем краткий план,
согласование неочевидных развилок с оператором, и только потом код.
Для мелких точечных правок — прямое действие без лишних вопросов
(баланс между «спросить» и «сделать» — оператор явно требовал не
разводить чрезмерную осторожность на пустом месте).

### 4.7. UI-кнопки/интерактивные виджеты (`ask_user_input_v0`) не работают в этом канале передачи

Обнаружено 2026-09-01/02 (оператором явно указано): интерактивные
кнопки выбора, генерируемые инструментом уточняющих вопросов, не
отображаются оператору в используемом им интерфейсе. **Уточняющие
вопросы — только простым текстом.**

### 4.8. Инструкции по эксплуатации — обычный `.txt`, не `.md`

На сервере заказчика нет удобного просмотрщика Markdown — только
Блокнот. Документ для оператора (`docs/DEPLOY.txt`) оформляется как
простой текст с ASCII-разделителями разделов, без `#`/`` ``` ``/
таблиц в markdown-синтаксисе. (Этот документ, `PROJECT_BACKLOG.md`, —
markdown, потому что читается разработчиком/моделью через GitHub, не
оператором через Блокнот на проде.)

### 4.9. Никогда не предполагать серьёзность бага по формальному статусу («RUNNING»)

Инцидент 2026-08-30/31 (служба Windows) научил: формальный статус
(«процесс запущен», «STATE: RUNNING») не гарантирует, что система
реально работает. Единственная надёжная проверка — свежесть данных
(время последней строки лога, время последнего собранного периода
архива), не факт существования процесса.

### 4.10. Перед выдачей готового файла проверять именно выдаваемый артефакт

Обязательное правило после инцидента 2026-09-04: оператор несколько раз
получил старую версию `energosphere_sync_test.go` под видом новой, из-за
чего зря повторял ручную замену файла и тесты.

Перед отправкой ссылки на готовый файл модель обязана проверить именно
тот файл, который будет выдан оператору:

- новые обязательные функции/строки должны присутствовать;
- старые функции/строки, которые должны быть удалены, должны отсутствовать;
- для Go-файлов по возможности выполнить `gofmt` и локальный тест/сборку
  соответствующего пакета;
- нельзя считать файл новым только потому, что он переименован в
  `READY`/`FINAL`;
- если после замены результат неожиданно остаётся старым, сначала
  перепроверить собственный выданный артефакт, а не просить оператора
  повторять ту же замену;
- формат передачи: **один точный путь → одна ссылка на один файл → одна
  команда проверки**. Не дублировать один и тот же файл несколькими
  ссылками и не выдавать несколько версий без явной необходимости.

### 4.11. На production-сервере — только короткие однострочные PowerShell-команды

Windows Server использует старый PowerShell. Многострочные блоки при
вставке могут зависнуть в приглашении `>>`. Поэтому на production:
- только короткие однострочные команды;
- без современных синтаксических конструкций;
- без `exit` внутри интерактивной консоли;
- серия проверок по возможности сводится к одному блоку, который в конце
  печатает только `OK` или `ERROR`.

На dev-машине многострочные команды допустимы, но короткие однострочные
проверки предпочтительнее.

### 4.12. Старый SQL Server — не использовать современные datetime-литералы в диагностике

Если ручной запрос содержит конкретную дату/время, использовать
`{ts 'YYYY-MM-DD HH:MM:SS'}`. Не считать `YYYYMMDDTHH:MM:SS`
универсально совместимым с этой инсталляцией SQL Server.

### 4.13. Операторский UI и эксплуатационный лог — на русском языке

Прямое правило владельца проекта от 2026-09-07: весь видимый оператору
интерфейс, названия статусов, фильтров, ошибок и обычных эксплуатационных
сообщений лога оформляются на русском языке. Английский сохраняется только
там, где это технический идентификатор/название протокола или внешней
системы (`Modbus`, `SQL Server`, `ID_PP`, `PointMains`, `SQLITE_BUSY`, имена
API/Go-полей и т.п.). При доработке старых экранов технические legacy-метки
в UI по возможности отображать русскими эквивалентами.

- Путь репозитория: `C:\mbgw-devkit\mbgw`

- Go-тулчейн: **`go1.20.14`** (вызывается явно этим именем, не просто
  `go`, — на машине может быть несколько версий). **Почему именно
  1.20.x, не новее** (см. `FINAL_TRD.md` §2, §6 — источник этого
  требования, не мой домысел): целевая платформа — **Windows Server
  2008 R2**. Начиная с Go 1.21 минимальная поддерживаемая версия
  Windows была поднята производителем Go — начиная с этой версии
  собранный бинарник физически не запустился бы на сервере заказчика.
  Go 1.20.x — последняя ветка, ещё поддерживающая эту старую ОС.
  **Практическое следствие** (подтверждено живьём, 2026-08-30 —
  раздел 5.1 ниже, инцидент с `golang.org/x/sys`): при добавлении
  ЛЮБОЙ новой зависимости нужно следить, чтобы САМА зависимость тоже не
  требовала более новый Go, чем 1.20.x, иначе сборка ЭТИМ тулчейном
  откажет с ошибкой вида `cannot compile Go 1.25 code`.
- **Почему сборка офлайн (`-mod=vendor`, `GOPROXY=off`)**: см.
  `FINAL_TRD.md` §1 — целевая сеть заказчика **изолированная, без
  интернета**. Не стилистическое предпочтение, а жёсткое требование
  среды эксплуатации.
- **Почему `CGO_ENABLED=0`, единый статический бинарник**: прямое
  следствие того же требования — ни один DLL/рантайм не должен
  доустанавливаться на сервере заказчика отдельно; весь перенос
  версии на прод в этом проекте буквально сводится к копированию
  ОДНОГО файла `mbgw.exe` (см. раздел 5.4/`DEPLOY.txt`) — так и
  оставалось верным весь ход разработки, ни разу не потребовалось
  ничего, кроме `Copy-Item`.
- Сборка (обязательно так, не иначе):
  ```powershell
  cd C:\mbgw-devkit\mbgw
  $env:GOOS="windows"; $env:GOARCH="amd64"
  go1.20.14 build -mod=vendor -o bin/mbgw.exe ./cmd/mbgw
  certutil -hashfile C:\mbgw-devkit\mbgw\bin\mbgw.exe SHA256
  ```
- `-mod=vendor` обязателен — сборка офлайн, зависимости в `vendor/`.
- Добавление новой зависимости — ТОЛЬКО через `go1.20.14 mod tidy` (не
  `go get pkg@latest`, который может подтянуть версию, требующую
  более новый Go, чем `1.20.14` — реальный инцидент 2026-08-30,
  `golang.org/x/sys/windows/svc`) и обязательно `go1.20.14 mod vendor`
  после. Проверять `git status`/`go.mod` diff на предмет каскадных
  изменений версий НЕСВЯЗАННЫХ пакетов после `mod tidy` — если такие
  появились, разбираться, а не коммитить бездумно.
- Проверка перед каждым коммитом (обязательная тройка):
  ```powershell
  go1.20.14 vet ./...
  go1.20.14 test -mod=vendor ./...
  go1.20.14 build ./...
  ```

### 7.9. [ОТЛОЖЕНО ДО РАБОТЫ С МЕРКУРИЕМ] Mercury KeepAlive вне общего physical I/O-lock

Внешний review 2026-09-05 отметил, что текущий путь Mercury `KeepAlive`

live-тестами и провести `KeepAlive` через тот же physical I/O-lock.

### 7.10. [ТЕХДОЛГ] Версия/commit внутри запущенного бинарника

Production-артефакт сейчас можно надёжно идентифицировать внешне через

### 7.11. [ИЗВЕСТНОЕ ОГРАНИЧЕНИЕ, НЕ БАГ] Akron: часовая дельта делится 50/50 на получасовки

Физический Akron даёт часовые точки накопительного `V`, а Энергосфера
ожидает получасовые значения. Реального профиля потребления внутри часа
из исходных данных восстановить невозможно.

Текущая договорённость: часовую дельту делить поровну на две
получасовки. Это сохраняет общий часовой объём, но не восстанавливает
реальный профиль потребления внутри часа. Не «улучшать» алгоритм без
нового источника более частых данных или отдельного требования заказчика.

### 7.12. [ТЕХДОЛГ, НИЗКИЙ] Лимит одновременных northbound-соединений

Review Claude 2026-09-08 отметил, что legacy northbound-серверы создают
`handleConn` goroutine на каждое принятое соединение без отдельного лимита.
В текущем изолированном контуре northbound не является production-путём
доставки Akron в ЭС, поэтому риск низкий и в post-review пакет №1/№2 не
входит. Если northbound снова станет эксплуатационным путём, добавить
ограничение одновременных соединений/очередь и тест на частые reconnect.

Первоначальный per-`deviceID` lock оказался недостаточен для двух разных

- `tcp_serial` -> `host:port`;
- `modbus_tcp` -> отдельный ключ прибора.

Session handshake и Reader используют один и тот же ключ. Добавлены
регрессионные тесты для shared COM / different COM / modbus_tcp.

### P1.1. [КОД ГОТОВ ЛОКАЛЬНО] Стартовый backfill через очередь poller

### P1.2. [КОД ГОТОВ ЛОКАЛЬНО] Инкрементальная обычная синхронизация с ЭС

SQLite `es_sync_cursor(device_id, point_id)` хранит последнюю
подтверждённую метку. Обычный worker не перечитывает 90 суток после
bootstrap. `ForceResyncRange` cursor не двигает.

### P1.3. [КОД ГОТОВ ЛОКАЛЬНО] Явная семантика `counter` / `interval`

`internal/interval.CounterDelta` используется и archive UI, и
Energosphere path. Пропуск больше часа и rollback счётчика трактуются
одинаково.

### P1.4. [КОД ГОТОВ ЛОКАЛЬНО] Safety-барьер перед записью в ЭС

- `NaN`/`Inf` запрещены всегда;
- `min_value`/`max_value` nullable, по умолчанию выключены;
- проверка после Factor/interval conversion;
- действует и на normal sync, и на ForceResync;
- редактируется через API/UI «Точки ЭС».

Текущий лог пишет понятное `БЛОКИРОВКА записи...`; отдельный буквальный
префикс `[ES-SAFETY] REFUSED` не является контрактом.

### P1.5. [КОД ГОТОВ ЛОКАЛЬНО] ЭС недоступна при старте

Начальный Ping больше не завершает worker навсегда. Retry начинается с
5 секунд и экспоненциально растёт до 30 секунд; после восстановления ЭС
worker продолжает работу.

### P1.6. [КОД ГОТОВ ЛОКАЛЬНО] Health-monitor полезной работы

Показываются heartbeat poller/current/archive/ЭС и SQLite Ping. Это
отдельная проверка полезной работы, не `STATE: RUNNING`.

## 11. Live-находки 10.09.2026 и каталог приборов из старой программы `Opros`

### 11.1. ИВК-ТЭР — подтверждён на реальном приборе

Физическая нестабильность линии объяснила серию прежних timeout: после
нормализации канала тот же МодбасШлюз без смены протокола начал читать реальный
ИВК-ТЭР и собирать функцию 65. Сравнение часовых значений с отдельной рабочей
программой показало совпадение самих измерений (в частности, прямого объёма и
среднего расхода); оставшиеся расхождения относятся к интерпретации времени и
названиям/отображению, а не к физическому чтению архива.

Профиль ИВК-ТЭР считать **live-confirmed по связи и часовому архиву**. Не
считать подтверждённой автоматическую установку часов: на реальном приборе она
не проверялась и для эксплуатации пока запрещена.

### 11.2. Что восстановлено из старой самописной `Opros.exe`

Старая программа многоприборная. Важно не смешивать её ветки: найденные ранее
`irga_session` / `irga_zapros` относятся к ИРГА и **не относятся к ИВК-ТЭР**.

Из формы выбора типа прибора в самом `Opros.exe` восстановлен актуальный порядок
типов (индекс ComboBox, 0-based):
- `0` — СЭТ / ПСЧ / СЭБ;
- `1` — FloBoss 103;
- `2` — Взлет КГ-411;
- `3` — Взлет ТСРВ-034 (в ресурсе старой программы помечен `???`);
- `4` — Взлет РСЛ-212;
- `5` — БВР.М;
- `6` — БКТ.М;
- `7` — СПТ961.2;
- `8` — ТС220;
- `9` — Ирга-2;
- `10` — Binom 337-339;
- `11` — Turbo Flow GFG;
- `12` — Multical 601;
- `13` — Binom 337;
- `14 (0x0E)` — Взлет ИВК-ТЭР.

В бинарнике одновременно присутствуют более старые диагностические строки вида
`tip:=...` (например, общий `tip:=2` перечисляет сразу несколько семейств). Их
нельзя использовать как каноническое соответствие современных пунктов формы:
при будущей разработке тип нужно привязывать к фактической ветке вызовов и к
живому прибору. Это правило добавлено после ошибочной первоначальной привязки
ветки ИРГА к ИВК-ТЭР.

Для **ИВК-ТЭР** отдельно подтверждено дизассемблированием ветки `0x0E`, что
первый запрос заводского номера — обычный Modbus RTU `FC04, IR 0x8002`; он
байт-в-байт совпадает с запросом МШ. Live 10.09.2026 дополнительно подтвердил
обычный Modbus/F65 путь: после восстановления физического канала МШ начал
читать прибор и часовой архив без фирменной сессии ИРГА.

В `settings.ini` старой программы найдены общие настройки `Poyas`, `Ensfera`,
`Synchron`, `Correct`, а также расписание коррекции. Это подтверждает наличие
в старом ПО механизма сравнения/ограничения коррекции времени на уровне общей
логики программы. **Точную команду записи часов именно для ИВК-ТЭР пока не
считать восстановленной**: автоматическую коррекцию ИВК-ТЭР не переносить в МШ
до отдельной привязки типоспецифичной ветки и live-теста в сервисном режиме.

База/настройки старой программы также показывают общий набор транспортных и
планировочных параметров: адрес/группа прибора, COM/TCP, baud rate, parity,
stop bits, timeout, часовой пояс, признаки автоматического опроса и коррекции.
Секреты/пароли из старых конфигурационных файлов в этот документ намеренно не
переносятся.

**Статус остальных приборов:** перечисленные семейства пока НЕ считать
подтверждёнными профилями МодбасШлюза. Это каталог «обнаружено в реально
работавшем ПО / кандидат на будущий профиль». Перед добавлением каждого в
production нужно отдельно восстановить его точные запрос/ответ, codec, семантику
времени/архива, сделать fixture-тесты и подтвердить на живом приборе.
