## ADR-001: ИВК-ТЭР использует mb_func65, а не mb_indexed_binary

**Дата:** 2026-07-09 (сессия разработки)

**Контекст.** FINAL_TRD.md §4 и IMPLEMENTATION_BACKLOG.md T7 назначают
ИВК-ТЭР стратегию `mb_indexed_binary` (простое чтение блока IR-регистров
по адресу `base_addr + index*record_regs`).

**Находка.** `str_arh_ivk_ter.pdf` (документация производителя на архивы
ИВК-ТЭР) прямым текстом утверждает: "Доступ к архивным записям
осуществляется... с помощью 65-ой функции ModBus" - для доступа **и по
индексу, и по времени**. `prtkl_Modbus_pril_1.pdf` (Приложение А,
описание функции 65) подтверждает: это родовой, общий для всей линейки
ВЗЛЕТ механизм чтения архивов ("номер массива", не привязан к конкретной
модели), уже используемый ТСРВ-024 через `mb_func65`.

**Решение.** ИВК-ТЭР переведён на `mb_func65` (тот же код, что и у
ТСРВ-024, различие только через `params.archive_type` - номер массива).
`mb_indexed_binary` оставлен в реестре стратегий (`allowedStrategies`) как
существующий, протестированный код на случай, если в будущем появится
прибор с действительно простым индексированным чтением IR-блока - но
`profiles/ivk-ter.yaml` больше его не использует.

**Обоснование.** Реальная документация конкретного прибора весомее, чем
формулировка в ТЗ, написанная до того, как эта документация была
внимательно прочитана и сверена с протоколом (`prtkl_Modbus_pril_1.pdf`
byte-in-byte). Расхождение подтверждено golden-векторами из документа
производителя.

**Подтверждено пользователем:** да (владелец архитектуры).

## ADR-002: Go toolchain для production — Go 1.20.14

**Дата исходного решения:** 2026-07-08  
**Пересмотрено:** 2026-09-05  
**Статус:** предыдущее решение о переходе на Go 1.26.5 отменено.

**Контекст.** FINAL_TRD.md §2 фиксирует "Ядро: Go 1.20.x" исходя из
целевых платформ Windows Server 2008 R2/2012. В ходе разработки была
сделана попытка перейти на более новый toolchain, однако проверка на
целевом Windows Server показала, что это нарушает совместимость:
сборки на Go 1.21+ на Windows Server 2008 R2 не являются допустимым
production-вариантом для этого проекта.

**Решение.** Production-сборки `mbgw` выполняются Go 1.20.14.
В `go.mod` сохраняется директива `go 1.20`. Для legacy-production
используется локальный toolchain Go 1.20.14 с офлайн/vendor-first
сборкой (`GOTOOLCHAIN=local`, `GOPROXY=off`, `-mod=vendor`).

Go 1.21+ и тем более Go 1.26.x не использовать для production-бинарников,
предназначенных для Windows Server 2008 R2. Более новый Go может
использоваться только для локальных экспериментов, если результат не
выдаётся как production-артефакт для legacy Windows.

**Обоснование.** Совместимость с фактической production-платформой важнее
успешной локальной компиляции и прохождения тестов на новом компиляторе.
Проверка на целевом сервере показала, что бинарники нового поколения Go
не подходят для Windows Server 2008 R2, тогда как Go 1.20.14 является
рабочей и подтверждённой базой сборки проекта.

**Не пересмотрено:** single-binary подход, `CGO_ENABLED=0`, vendored
зависимости и возможность офлайн-сборки остаются в силе.

**Подтверждено пользователем:** да (владелец архитектуры).

## Незакрытые вопросы, требующие аналогичного решения в будущем

- **Меркурий: команды 0x03/0x04/0x16** используются как "generic read/write
  parameter" вместо жёстко прописанных в CONTRACTS.md сигнатур
  (`Protocol` interface с `BuildFrame`/`ParseFrame`/`Transact` для единого
  `Request`/`Response`). Фактическая реализация (`protocol/merkuriy`,
  `protocol/akron`) использует набор конкретных билдеров вместо этого
  общего интерфейса. Работает, протестировано, но формально отклоняется
  от CONTRACTS.md §2. Не оформлено отдельным ADR, так как не обсуждалось
  явно с пользователем - помечено здесь как известное расхождение.

## ADR-003: Alarm/квитирование в internal/monitor отложены (не реализованы)

**ата:** 2026-07-15 (сессия разработки)

**онтекст.** `LLD.md`'s `internal/monitor` spec требует `alarms.go` и
DoD «тревога поднимается/квитируется» - SCADA-style alarm-механизм
(правило -> Alarm -> Acknowledge).

**ешение.** `internal/monitor` реализован **только** как чистая шина
событий (`Bus.Publish`/`Subscribe`) - `AlarmRule`/`Alarm`/`Acknowledge`
не реализованы вообще (файл `alarms.go` не создан).

**боснование.** еальный профиль использования этого проекта - приборы,
опрашиваемые по расписанию раз в час/сутки, часто по модемному каналу с
дозвоном, а не непрерывно опрашиваемые SCADA-узлы. лассическая
SCADA-тревожность (событие -> немедленная тревога -> обязательное
квитирование оператором) плохо подходит для одиночного неудачного
дозвона - такое событие ожидаемо и уже покрыто retry/backoff, поднимать
по нему тревогу означало бы приучать оператора игнорировать тревоги
("alarm fatigue"). равильные условия тревоги для этого профиля
использования (например, "не удалось получить архив N дней подряд", а не
"один неуспешный опрос") ещё не определены и требуют отдельного
продуктового решения, а не технической реализации вслепую по букве Т.

**то сделано вместо этого.** `Bus` спроектирован так, что добавление
alarm-слоя позже не потребует переделки: `Persister`-интерфейс и модель
`Event` уже пригодны для этого, `AddAlarmRule`/`Alarms`/`Acknowledge`
можно добавить отдельным файлом `alarms.go` без изменения `bus.go`.

**одтверждено пользователем:** да (владелец архитектуры) - явное решение
отложить, не техническая недоработка.

## ADR-004: Windows Service и ручной запуск используют единый server core

**Дата:** 2026-09-08

**Контекст.** В production наблюдалось состояние Windows Service
`RUNNING`, при котором полезный опрос отсутствовал. Ревизия показала, что
`svc.Run` был запущен в отдельной goroutine и жизненный цикл SCM фактически
не владел жизнью основного server/poller. Отдельно существует риск быстрого
рестарта: SCM уже считает службу остановленной, а старый процесс ещё держит
транзакцию с прибором.

**Решение.** Вынести полезную работу в единый `runServerCore(ctx, onReady,
runningAsService)`. Ручной режим вызывает его напрямую. В режиме Windows
Service Service Handler владеет context и запускает тот же core. Состояние
`Running` отправляется SCM только после фактического запуска poller. На
`Stop/Shutdown` Handler переводит службу в `StopPending`, отменяет context и
ждёт полного возврата core; только затем служба считается остановленной.
Core, в свою очередь, ждёт не только per-device worker'ы poller, но и
HTTP-операции, которые реально используют физический канал вне poller:
«Проверить прибор» и фоновый принудительный переопрос архива. После начала
shutdown новые такие операции не принимаются. Поэтому `Stopped` нельзя
получить, пока старый процесс ещё держит COM-порт/конвертер.

Ошибка запуска/работы core при ручном режиме возвращает ненулевой код
процесса; ошибка пути Windows-службы также не маскируется успешным exit code.

`install-service` должен безопасно обновлять уже существующую службу и
настраивать автоматический запуск и Recovery после аварий.

**Обоснование.** Статус SCM и полезная работа становятся одним жизненным
циклом; исключается раннее `Running` и пересечение старого/нового процесса
на физическом I/O при штатном рестарте.

**Подтверждено пользователем:** да.

## ADR-005: Watchdog перезапускает только реальную Windows-службу и ведёт отдельный журнал

**Дата:** 2026-09-08

**Контекст.** Требуется защита от молчаливого глобального зависания опроса.
Простой критерий «давно нет успешных данных» неверен: все приборы могут быть
физически недоступны, но шлюз при этом исправно выполняет задания. Кроме
того, аварийный `os.Exit` при ручном запуске оставил бы шлюз выключенным,
потому что некому поднять процесс заново.

**Решение.** Watchdog следит за heartbeat центрального poller и прогрессом
per-device операций/очередей. Ошибка ответа прибора не является зависанием.
Один зависший прибор — предупреждение; глобальный отказ фиксируется только
при остановке центрального механизма либо зависании всех активных приборов.

Отдельный критерий по просроченному `nextDue` намеренно исключён после
финальной ревизии: `scheduler.Tick()` штатно переносит срок вперёд, а задачи
занятого прибора могут долго ждать в его FIFO. Реальное зависание самого
`scheduler.Tick`/`drainAsync` автоматически останавливает центральный
heartbeat; зависание worker'ов определяется по отсутствию их прогресса.

Если процесс действительно запущен SCM как Windows-служба, подтверждённый
глобальный stall после записи причины завершает процесс ненулевым кодом, а
Recovery SCM запускает его снова. При ручном запуске/Планировщике watchdog
никогда сам не завершает процесс: только красный статус в UI `/health` и
журнал.

Диагностический журнал службы хранится в отдельной
`mbgw_service_log.db`, а не в основной `mbgw_server.db`; аварийная запись
имеет ограниченный таймаут. Ретенция — 30 дней, очистка при старте и раз в
сутки.

**Обоснование.** Механизм восстанавливает только действительно зависший
процесс, не превращает отсутствие связи в цикл рестартов и не ухудшает
текущий ручной production-режим. Отдельная БД сохраняет диагностику при
проблемах основной SQLite.

**Подтверждено пользователем:** да.

## ADR-006: Коррекция времени ИВК-ТЭР остаётся ручной сервисной операцией

**Дата:** 2026-09-08

**Контекст.** ИВК-ТЭР добавляется в штатный production-опрос: идентификация,
текущие данные, часы и архив функции 65. Документация прибора ограничивает
запись часов HR `0x8000` режимом Service/Setup. Автоматический poll не должен
пытаться обходить это ограничение.

**Решение.** Обычный опрос только читает `current_time` и показывает
расхождение. В UI состояние называется «Коррекция: только вручную, в
сервисном режиме прибора». Для записи используется явная команда `set-time`,
которая берёт production-конфигурацию из `mbgw_server.db`, отказывается
работать при запущенном основном экземпляре шлюза, требует ручного перевода
прибора в Service/Setup и после функции 16 перечитывает часы.

**Обоснование.** Нельзя превращать ограничение коммерческого прибора в
«недоделку» и нельзя экспериментально обходить сервисную защиту. Явная
операция делает физическое вмешательство контролируемым и исключает
параллельный I/O основного сервера.

**Подтверждено пользователем:** да.
