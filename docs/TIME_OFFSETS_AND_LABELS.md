# Временные метки, сдвиги и связанные особенности — сводка находок

Документ собирает всё, что было выяснено о временных метках архивных
записей, особенностях самой Энергосферы и связанных подводных камнях —
по итогам многочасовых расследований 2026-08-25...27. Цель — чтобы в
будущем при похожих симптомах («данные не совпадают», «в ЭС не то время»,
«архив выглядит неправильно») не пришлось заново проходить весь путь
расследования с нуля.

## Коротко — если совпадений нет, начните отсюда

Если числа/время «не сходятся» между нашей системой, ЭС и родным ПО
прибора — почти наверняка это ОДНА из уже известных причин ниже, а не
новый баг. Проверяйте по порядку:

1. Правильно ли размечена метка периода (конец интервала, не начало)?
2. Не путается ли «отчёт ЭС» (со своим смещением показа) с «таблицей
   `Mains`» (реальными сырыми данными)?
3. Для Akron — не забыт ли факт, что `V` (объём) — счётчик-одометр,
   нужна РАЗНИЦА соседних показаний, а не само число?
4. Не запрошен ли/не сохранён ли ещё не завершившийся период?

Дальше — подробности по каждому пункту.

---

## 1. Метка периода = КОНЕЦ интервала, не начало

**Правило (актуально с 2026-08-27):** запись архива с меткой `10:00`
означает «данные за интервал `[9:30, 10:00)`» — то есть метка ставится
на МОМЕНТ ЗАВЕРШЕНИЯ периода, а не на его начало.

Это единое соглашение для **обоих** типов приборов:
- **Akron** — так было изначально, часовой архив, никогда не менялось.
- **ВКМ** — до 2026-08-27 подписывался НАЧАЛОМ периода (получасовка
  `[9:30,10:00)` называлась `9:30`, не `10:00`). Исправлено в
  `internal/device/vkm_hourly.go` (см. `persistVKMHourly`).

**Почему это важно:** несовпадение соглашения между Akron и ВКМ внутри
одной и той же системы выглядело как «данные ВКМ опаздывают на
полчаса-час» — хотя на самом деле опоздания не было вообще, только
разное название одного и того же интервала.

**Если снова столкнётесь с "опозданием" данных ВКМ** — первым делом
проверьте, не относится ли это к записям, собранным ДО фикса
2026-08-27 (они всё ещё размечены по-старому и не мигрируют
автоматически, см. раздел 5).

## 2. Отчёт/график ЭС всегда показывает данные со сдвигом ПОКАЗА на один шаг вперёд

**Обнаружено и математически доказано 2026-08-27** на примере
СОВЕРШЕННО ПОСТОРОННЕГО электросчётчика (ID_Channel=121022, никак не
связанного с нашей системой) — значит это встроенное поведение самой
ЭС, а не что-то, что вносим мы.

**Суть:** если в таблице `Mains` реально лежит запись с
`MeasureDate = 01:00:00`, отчёт/график ЭС покажет её значение в строке
`01:30` (для получасового шага) — то есть отчёт подписывает каждую точку
данных МЕТКОЙ СЛЕДУЮЩЕГО шага относительно того, что реально в базе.

**Доказательство (2026-08-27, канал 121022):**

| В базе `Mains` (реально) | В отчёте ЭС (показ) |
|---|---|
| `00:30 = 0.1363` | `01:00 = 0.1363` |
| `04:30 = 0.13375` | `06:00 = 0.13375` |
| `06:30 = 0.13685` | `08:00 = 0.13685` |
| `08:30 = 0.13665` | `10:00 = 0.13665` |

Сдвиг постоянный — **90 минут** для получасового шага в данном
конкретном случае (соответствует "на один шаг + ещё немного"; для
приборов с другим шагом опроса сдвиг отчёта может отличаться —
не проверялось на других шагах, только на получасовом).

**Практическое следствие:** при любой сверке «что в отчёте ЭС» vs
«что реально в БД» vs «что показывает родное ПО прибора» — НЕ
сравнивайте отчёт ЭС напрямую с БД по одинаковым меткам. Либо сверяйте
отчёт с родным ПО прибора (оба показывают «человеческое», логически
верное время), либо сдвигайте метки БД на шаг вперёд перед сравнением с
отчётом.

## 3. Настройка `time_shift_minutes` (`-90`) — компенсация ВТОРОГО, отдельного явления

**Где:** вкладка «Подключение к ЭС» в `/admin`, поле «Сдвиг времени для
ВКМ (минут)».

**Что это НЕ:** это НЕ то же самое, что явление из раздела 2 (сдвиг
показа отчёта). Раздел 2 — особенность ЛЮБЫХ данных в ЭС, не зависящая
от нас. Раздел 3 — особенность ТОЛЬКО прямой записи в `Mains` в обход
штатных драйверов ЭС.

**Суть:** когда мы сами пишем строку в таблицу `Mains` напрямую (минуя
драйвер прибора со стороны ЭС), сама база/ЭС раскладывает такие ПРЯМЫЕ
записи со сдвигом примерно на **90 минут** относительно того, что мы
реально записали в поле `MeasureDate`. Точный механизм на стороне ЭС не
установлен (это может быть связано с часовым поясом — в шапках отчётов
родного ПО прибора указано `UTC+4`, а ЭС предположительно хранит
внутренне в UTC и как-то доп. смещает при приёме прямых `INSERT`).

**Почему число подобрано ИМЕННО так:** два явления (раздел 2 и раздел 3)
СКЛАДЫВАЮТСЯ и в сумме дают ощущение «всё смещено», но по отдельности они
идут в РАЗНЫЕ стороны и примерно взаимно гасятся при `time_shift_minutes
= -90`. Подтверждено вручную, число к числу, на реальных данных
2026-08-27 (расхождение < 0.5% для всех проверенных часов, кроме одного
локального, не связанного со сдвигом времени случая — см. раздел 6).

**Касается кого:** ТОЛЬКО приборов, чьи данные мы пишем НАПРЯМУЮ в
`Mains` (сейчас — ВКМ, через `es-sync`). НЕ касается приборов, чьи
данные ЭС забирает САМА через эмуляцию прибора (сейчас — Akron, через
northbound). Правило масштабируется на будущее: если новый тип прибора
подключается через прямую запись — сдвиг для него актуален; если через
эмуляцию — не актуален, независимо от типа/марки прибора.

**Если появится второй сервер ЭС** (не подтверждено, но теоретически
возможно) — сдвиг может отличаться для другого сервера, тогда
потребуется настройка на подключение, а не глобальная (сейчас архитектура
предполагает одну ЭС на объект — см. `es_connection`, единственная
строка в таблице).

## 4. Akron: поле `V` — накопительный счётчик (одометр), не расход за период

**Обнаружено 2026-08-23**, ошибочно принято за «аномалию данных» на
несколько часов расследования, прежде чем разобрались.

**Суть:** сырое значение `V` в архиве Akron — это ПОКАЗАНИЕ СЧЁТЧИКА на
момент снимка (сколько прошло ВСЕГО с начала эксплуатации), а не расход
именно за этот час. Чтобы получить реальный часовой расход, нужно взять
**разницу** между показанием текущего часа и показанием предыдущего.

**Реализовано:** `internal/web/api_archive.go`, `paramCumulative["V"] =
true`, функция `applyCumulativeDelta` — архивная вкладка UI уже
автоматически считает разницу, оператору не нужно делать это вручную.

**ВКМ так не работает** — его `S`/`ST` это уже готовые суммы за период,
подтверждено сверкой с официальным отчётом прибора независимо (см.
`internal/integration/energosphere_sync.go`, package doc). Суммировать
несколько периодов ВКМ (для «по суткам»/«по месяцам») — правильно.
Суммировать несколько периодов Akron `V` — НЕПРАВИЛЬНО, там нужна
разница крайних точек, не сумма.

## 5. Смена соглашения о метке (раздел 1) не мигрирует старые записи автоматически

Когда 2026-08-27 поменяли разметку ВКМ с «начало периода» на «конец
периода» — уже накопленные в базе строки остались под СТАРОЙ меткой.
Новые записи идут уже по новому соглашению. Простой upsert (перезапись
по точному совпадению времени) НЕ убирает старые записи — они остаются
висеть под своей старой (теперь не совпадающей ни с чем) меткой рядом со
свежими правильными.

**Решение:** `internal/device/vkm_reload.go`,
`ForceReloadVKMHourly` теперь сначала УДАЛЯЕТ весь запрошенный диапазон
(с запасом в один период с каждой стороны — захватывает оба соглашения
разметки), затем собирает заново. «Принудительный переопрос» с
достаточно широким диапазоном — единственный надёжный способ
мигрировать старые данные на новое соглашение.

**Если снова придётся менять соглашение о разметке в будущем** (не
дай бог, но вдруг) — используйте тот же паттерн: удаление диапазона
перед повторным сбором, а не полагайтесь на upsert.

## 6. Защита от сохранения ещё не завершённого периода

**Обнаружено 2026-08-27**: при «Принудительном переопросе» с полем «по»
= сегодняшняя дата без явного ограничения система могла запросить и
сохранить период, который на момент запроса ещё физически не закрылся
(например, в `12:45` сохранить запись с меткой `13:00`, хотя интервал
`[12:30,13:00)` ещё не закончился).

**Опасность:** если такое неполное значение уйдёт в ЭС — оно ляжет как
будто период уже закрыт, и последующая ПРАВИЛЬНАЯ (полная) версия того
же периода может не переписать его, если механизмы приёма ЭС считают
время уже «занятым».

**Решение:** `internal/device/vkm_reload.go`, `ForceReloadVKMHourly`
жёстко обрезает верхнюю границу диапазона до «последнего периода,
который уже гарантированно закрылся к текущему моменту» — независимо от
того, что выбрал оператор в поле «по».

**Akron этому не подвержен** — там границу определяет сам прибор через
собственную индексацию (i=1 — его "самая свежая" запись), мы не
вычисляем границу сами по настенным часам, как для ВКМ.
